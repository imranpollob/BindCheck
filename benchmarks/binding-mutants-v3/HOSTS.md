# B3 hosts

**TEST benchmark (the paper calls it B3). Never share it with a tool-building lane.**

**Naming:** the directory is `binding-mutants-v3`, and the paper calls this benchmark **B3**. EVAL-PLAN's old "B3" (the circuit-bug control from zkbugs / the 0xPARC tracker) is **superseded** (orchestrator decision, 2026-11-25).

Five hosts, chosen 2026-11-25. All five hosts are **excluded from the hunt pool** from now on.

Each host meets all of the following:
- it has a circuit or guest, a verifier and an EVM consumer;
- it has an explicit open-source licence;
- it passes `dataset/audit-sweep/tools/check_holdout.py` (`ALLOWED`; rerun 2026-11-25 on the exact repo names below);
- its `v2_family_id` is outside the 13 families of the 26 repos named in `LABELS-v1.csv`, and its project name matches no LABELS `family` value;
- it is not a B2 host (redpacket, privacyvaults, orc);
- it builds locally and has an executed honest path.

## Family and lineage checks
- The 26 repos named in `LABELS-v1.csv` map to 13 `v2_family_id`s in `dataset/source-corpus-v2.csv`. No host is in that set:
  - zkerc20: `v2-family:83030d11e70dd6972919`
  - dark: `v2-family:91ddff3752972a26505e`
  - davinci: `v2-family:980859c1054871b9b38a`
  - kakushi: `v2-family:bf91ad0a00e7eea80a9b`
  - xchain: not in the corpus
- zkerc20, dark, davinci and kakushi are spent-family-ledger (freeze-2) rows. xchain is a new repository.
- **Lineage, signed off by the orchestrator 2026-11-25:**
  - kakushi's `KakushiPool.withdraw` has a Tornado-shaped interface: a Noir rewrite with no shared code.
  - zkerc20's circuit header says `reference: tornadocash/tornado-core`, but the design is an original 8-in/2-out UTXO split.
  - Both are accepted as outside the "Tornado Cash" family.
- xchain's organisation also owns `fiit-ba/hopinzero`, which is **FORBIDDEN** (reserved held-out family `v2-family:4204dfab64a09349325e`). That is a different codebase: a Circom options app according to its corpus metadata. It was **not opened**.

## Build deviations from the pinned repos (all documented, none in a consumer or committed verifier)
- **zkerc20:** `circuits/verifier.sol` is not committed upstream.
  - It was generated by the host Makefile recipe (`circom 2.2.2 --r1cs --wasm`; `snarkjs 0.7.6 groth16 setup` with Hermez `powersOfTau28_hez_final_19.ptau`, blake2b `bca9d8b0…0887`).
  - **One local phase-2 contribution** was added, because the bare Makefile setup leaves γ = δ, which is a forgeable key and would be a P4 artefact in the clean host.
  - Hashes: zkey sha256 `a6897158…a113b9`; `verifier.sol` sha256 `e70c2a5c…be073` (checked by `export-baselines.sh`).
  - The circuit has 331,643 constraints and 12 public inputs.
- **Tool-facing trees exclude:**
  - host tests, mocks under `test/`, Certora specs and fuzz harnesses;
  - audit documents (`AUDIT.md`, `docs/audit-*`);
  - deploy scripts and UIs.
- **Noir in-file unit tests** (`mod tests` / `#[test]` at the tail of each `.nr`) are truncated in dark and kakushi, identically for clean, mutant and decoy trees. Reason: their `should_fail_with` messages name the assertion that a mutant deletes. Every test block was checked to be the file's tail, and `nargo check` passes on the truncated sources.
- dark keeps `contracts/src/mocks/` because it is under the host's `src/`. kakushi keeps only the pool closure (`privacy/KakushiPool`, `PoolZeros`, `PrivateCallExecutor`, `KakushiPoolFactory` plus the interfaces and libs they import), with its whole `packages/zk` Noir workspace.
- xchain keeps the six route crates, including `host/`, because it is a Cargo workspace member needed for `cargo check`.
- Dependencies are pinned by `fetch-deps.sh` into ignored `results/raw/B3/deps`: forge-std v1.15.0, risc0-ethereum v3.0.1 (+OZ submodule), npm lockfiles under `deps/`, circomlib 2.0.5, and `@aztec/bb.js` 5.0.0-nightly.20260522 via npm. The orchestrator approved the bb.js install; a direct bb binary download was refused by the permission classifier and not retried.

## Known baseline issues (pre-registered as KB-1/KB-2 in `MATCHING.md`; orchestrator decision: keep both hosts)
- **KB-1 (xchain):** none of the six guests commits a Steel block commitment, and the Connector validates none, so the remote chain state is not anchored on-chain. The connector address that a guest queries is a private, uncommitted input.
- **KB-2 (zkerc20):** the commitment-tree insertion function is `public` on the token contract.

Both are source read-through observations with no proof built. They are logged in `HUNT-LEADS.md`. No B3 mutant's GT mechanism is a KB mechanism.
