## 3. Output-use coverage and application decisions

### 3.1 Payy rollup — calibration only

The final public vector is `old_root`, `new_root`, `commit_hash`, followed by
1,000 message words at the pinned source revision. `RollupV1` passes the
complete vector unchanged to a verifier selected by the configured registry.
It checks the old root, binds the new root through validator signatures and a
state update, decodes messages, marks mint identities spent, and attempts burn
token transfers. `commit_hash` reaches the verifier, but the pinned
`verifyCommitHash` consumer hook is empty. Payy therefore supplies an exposed
subset-use case, not an assumption that subset use is easier.

The concrete obligation is: every committed mint-spent write or burn transfer
in an accepted transition must match exactly one proof-authorized inner
message occurrence with the same identity, asset, amount, beneficiary and
domain; required occurrences must be covered and padding must authorize no
effect.

The family has pinned source, N=1000 constraints/ABI/keys/verifiers, real
proofs and accepted local replays, plus historical and repaired revisions.
The exact N=8 `agg_final` key and accepted bundle, full-relation extraction,
joint encoder and a measured equal-information advantage remain absent.
D1P-10's null feasibility result makes further selected-cone tuning
unjustified. Payy is retained as candidate 3 only for calibration and repair
controls.

The documented policy and audit evidence remain separate. Source, whitepaper
and earlier reports support the state-transition and message-occurrence
intent. AuditOne's landing page reports a November 2024 Rollup contract audit
with 1 high, 1 medium, 5 low and 3 QA items, but its detailed report was not
accessible and the stated commit pair could not be mapped to the public
mirror. The public advisory is not an audit; [T20](T20.md) controls its source
and replay claims. D1P-11 neither validates nor relabels any finding.

### 3.2 WarpToad — candidate 1

The Noir withdraw relation exposes eleven fields: nullifier, chain ID, amount,
giga root, destination local root, Aztec WarpToad address, fee factor,
priority fee, maximum fee, relayer address and recipient address. The
Solidity consumer constructs this exact vector, using `block.chainid` and its
configured application address, and passes it to a fixed verifier. Roots and
nullifier state guard acceptance; amount, fee fields and beneficiaries drive
the mint split. Any external caller may relay a proof, but success requires an
accepted proof and roots.

The concrete obligation is: a successful mint must be authorized by one
source commitment for the configured application and domains, consume the
same nullifier once, and conserve exactly `amount` wrapped units between the
bounded relayer fee and recipient mint.

Pinned Noir, Solidity, TypeScript proving and honest-test sources are
available. A compiled circuit was inventoried earlier, but the exact
source/ACIR/ABI/VK/generated-verifier correspondence and an accepted proof
have not been validated. Compiler compatibility, Merkle/Poseidon assumptions,
fee/basefee arithmetic, token mint semantics and fork-free initialization
remain implementation gaps. These are small enough for a standalone
correspondence gate, so WarpToad ranks first. No application-specific audit
was located in the bounded search; that is not evidence of no findings or a
negative control. The source's existing defect-warning comment is exposure,
not a D1P-11 vulnerability finding.

### 3.3 0xbow Privacy Pools — contingent candidate 2

`Withdraw(32)` has two outputs followed by six public inputs: new commitment
hash, existing nullifier hash, withdrawn value, state root, state-tree depth,
association-set-provider root, ASP-tree depth and context. `PrivacyPool`
checks or commits effects from all eight signals and passes the complete
vector to the Groth16 verifier. It spends the nullifier, inserts the new
commitment and transfers value to the processor.

`BatchRelayer` is also a useful subset consumer: it directly accumulates only
`withdrawnValue`, while each nested pool call and its context binding handle
the other seven signals. It checks the declared nonempty batch and total,
then splits the total between one recipient and fee recipient. This layered
subset is not presumed easier than the all-output pool transition.

The concrete obligation is: each proof occurrence must authorize exactly one
nullifier consumption, commitment insertion and withdrawal; the batch must
include every occurrence once and conserve the multiset total through exactly
one bounded recipient/fee split, with no omission, duplication or reuse.

Pinned source and an inventory of R1CS/WASM/zkey/vkey artifacts exist, along
with source-level honest tests. Exact artifact/key/verifier correspondence and
an accepted fork-free batch fixture remain missing. The current frontend has
no Circom/R1CS intake and no aggregation/splitting or nested-array consumer
model. Candidate 2 is therefore contingent on an explicit scope decision,
not an authorization to expand implementation.

Auditware's report covers ancestor `f0b8fe5...`; GitHub reports the screened
`d494b63...` pin 335 commits ahead and zero behind. The report lists three
medium and three low items concerning token approval, root-history overwrite,
Poseidon provenance, association-set/root availability, root indexing and
relayer fee bounds, with reported mitigation statuses. It omits the screened
`BatchRelayer` path and does not validate the later revision. The older Oxorio
v1 audit concerns a different `proofOfInnocence.circom` architecture. Neither
record is vulnerability ground truth or a negative control here.

### 3.4 Aztec v6 epoch rollup — excluded

`EpochProofLib` assembles a complete verifier vector covering previous/end
archives, outbox hash, inbox rolling hashes, checkpoint headers, per-checkpoint
fee recipients and amounts, chain/version/configuration values, prover ID and
blob-accumulator data. Immediate consumer effects use a subset: outbox
insertion, fee and prover-reward accounting, proven-tip advancement and
activity. Other values principally bind the verifier and admission guards.

The concrete obligation would require every inserted outbox root and each
fee/reward occurrence to match the same proof-authorized checkpoint range,
with pending messages later consumed at most once. The application nevertheless
requires recursion, checkpoint aggregation, blob/KZG checks, committee
attestations, deferral and reward accounting, while a self-contained pinned
producer/ABI/VK/proof route was not recovered. It is excluded as intractable
for the current fragment, not classified safe or insecure.

The pinned `SECURITY.md` states that the network is under internal and
external review and gives aggregate v4/v5 counts, not v6 epoch-rollup
findings. No exact v6.0.0 audit was located. The v6.0.0 release pins source,
Noir and binary provenance but is not audit evidence.
