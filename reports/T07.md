# T07 — Direct Foundry invariant baseline vs the trace checker

Authorized defensive research on self-authored contracts in a local Foundry EVM. This is the **first, simple baseline**, not the strongest verification baseline intended for the paper. The T01 Groth16 setup is a toy with public, recomputable entropy; nothing here speaks to adversarial soundness. Finite enumeration over two fixtures only: no claim about other amounts, witnesses, circuits or transaction sequences, and the baseline does not discover proof witnesses.

## 3. Method
- **Baseline** (`BaselineProperty.sol`, Solidity): reads raw storage (`vm.load`) before/after each call. After a successful settlement it checks (a) pre/post commitment equal the public old/new commitments; (b) every active row had a funded, exact-amount, unconsumed entry that is consumed afterwards; (c) the sum of newly consumed amounts equals the `consumedBacking` change. After a revert it checks all protected state is unchanged. It is exposed as `_evaluate` (returns a result; needed for the violating cases) and `assertCoverageProperty` (the assertion form). It imports nothing from the JavaScript checker.
- **Disclosure:** the baseline is an extension of the T04–T06 raw-storage oracle assertions, written by the same author with the same semantics. It is not independent researcher validation. Shared assumptions are listed in the file header: public-input layout, active iff flag == 1, deposit identity `(batchId,row)`, 1 unit = 1 wei, the backing policy, the storage layout, and that proof acceptance is not checked.
- **Enumeration** (`T07Baseline.t.sol`): fixtures original `[100,250,0,40]/[1,1,0,1]` and padded `[100,250,0,0]/[1,1,0,0]`; every subset of **active** rows funded (inactive row 2 never funded); limits 0–4 for the mutant and repaired consumers; the correct consumer once per subset. Each case deploys a fresh consumer against the real generated verifier and the real proofs, executes, evaluates the baseline, exports a record and writes the baseline result to a separate directory. The two proofs are verified in `setUp`.
- **Checker side:** `compare_baseline.js` runs the unchanged checker over `records/` only. Baseline files and a design-intent prediction (computed from the configuration alone) are used only by the comparison, never as checker input. Record execution ids are opaque (`c-001`…`c-132`).

## 4. Proof-acceptance inference and verifier enforcement
The checker infers proof acceptance from (i) a recorded verifier call whose calldata carries the settlement's public inputs and (ii) a successful outer call. **That inference is valid only if the consumer enforces the verifier result;** the call and the success alone are insufficient, and the record cannot show the enforcement. This is now stated in the spec's `assumptions`, in the checker's notes for settled verdicts, and here. Confirmed for each evaluated consumer (`verifier_enforcement.txt`):
```
BackedBatchConsumer.sol:86              if (!verifier.verifyProof(pA, pB, pC, pubSignals)) revert InvalidProof();
MutantBackedBatchConsumer.sol:95        if (!verifier.verifyProof(pA, pB, pC, pubSignals)) revert InvalidProof();
RepairedPrefixBatchConsumer.sol:104     if (!verifier.verifyProof(pA, pB, pC, pubSignals)) revert InvalidProof();
```
Behavioral confirmation (`test_eachEvaluatedConsumerEnforcesTheVerifierResult`): for each consumer, an altered public amount with the original proof (all escrow funded, old commitment matching, so no other check would reject first) reverts with exactly `InvalidProof()` and leaves state unchanged.

## 7. Does BindCheck show an advantage yet?
**Not on this property.** The direct Foundry assertion matches the checker on all 132 cases in every compared dimension, is shorter, and needs no exporter. Differences that exist but were not exercised by a differentiating case, so they are not claimed as advantages: the checker works offline on records (including from sources without the test harness) and returns `INCONCLUSIVE`/`EVIDENCE_ERROR` on absent or inconsistent evidence (unit-tested in T06, never triggered by these real records); it cross-checks that the verifier received the settlement's public inputs, which the baseline does not check. Both methods share the same semantic specification, so neither validates it, and neither finds a defect that the shared specification does not describe.

## 8. Limitations
- Two fixtures, three consumers, one property, one circuit. The enumeration is exhaustive only over that finite space (funding subsets × limits 0–4).
- Baseline and checker share author, semantics, and observation of the same executions; agreement shows implementation consistency, not correctness of the policy.
- Proof acceptance is inferred (§4); the verifier's return value is not captured. Only the recorded batch's rows are observed.
- Public inputs and funding amounts are on-chain; commitments are unsalted. The T02 off-curve gas observation remains open.
- Not run: stronger baselines (Halmos/symbolic, stateful fuzzing with random proofs), circuit-level tools, additional bug classes, fresh-machine rehearsal.
