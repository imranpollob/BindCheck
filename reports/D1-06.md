All six queries timed out at 300 seconds with 4 GiB memory limit under
cvc5 finite-field `split` mode. The solver scalability limit on the N=8
Payy circuits is the established blocker.

**CEGAR assessment on N=8:** The CEGAR mechanism adds overhead (concretization
solver calls + multiple iterations). On queries that already time out at
300 s, CEGAR would make each iteration individually time out or produce
iterations that consume their own 300 s budget. The abstract-then-refine
strategy cannot help when the solver cannot handle the full constraint set
within resource limits — it would need the full constraint set eventually
(for UNSAT proofs) or at concretization (for candidate confirmation).

No new N=8 runs were attempted. The solver scalability limit is not a
method-level problem (it affects all SMT-based methods equally) but it
blocks the evaluation of CEGAR's advantage on real circuits.

## CEGAR mechanism assessment

### What CEGAR provides

1. **Concretization check**: Candidates are verified against full ACIR before
   being reported as violations. This catches over-approximation errors that
   would affect B3 (manual summary) style approaches.

2. **Automatic constraint selection**: No analyst-written summaries needed
   (0 LOC vs B3's ~25 LOC). Constraints are selected by witness reachability.

3. **Correct verdicts**: Same results as monolithic (D1-03/B2) on all cases.

### What CEGAR does NOT provide on these cases

1. **Speed advantage**: CEGAR is 3–9% slower than monolithic due to
   concretization overhead. The abstract phase cannot skip constraints because
   the one-hop transitive closure from the 18 model witnesses covers all
   26/35 ACIR constraints.

2. **Selective refinement**: On N=9 circuits with 26/35 constraints, every
   constraint is reachable within one hop from the public witnesses. The
   refinement adds all constraints in a single step, making iteration 1
   equivalent to monolithic solving.

3. **Scalability improvement**: The solver scalability limit (N=8 Payy
   timeouts) is not addressed. CEGAR operates above the solver; it cannot
   make individual solver calls faster.

### Recommendation

**The current method does not support the claimed contribution.** The
consumer-directed CEGAR mechanism is correct and sound, but it provides no
measurable advantage over monolithic joint solving on the available cases.
The solver scalability limit blocks evaluation on real circuits. The
hypothesized advantage (selective constraint refinement) requires circuits
where the constraint set is large enough that the transitive closure from
candidate witnesses covers only a fraction of constraints — this is not
demonstrated.

**Options:**
1. **Close D1.** Report the negative result honestly. The CEGAR mechanism
   works but doesn't justify the contribution claim.
2. **Narrow to solver engineering.** The scalability blocker (cvc5 FF solver
   on RANGE-heavy circuits) is the root cause. Addressing it would enable
   real-case evaluation but is solver work, not method work.
3. **Create larger synthetic circuits.** Would test selective refinement but
   risks benchmark tuning. The advantage on synthetic cases doesn't transfer
   to real circuits if the solver can't handle them.
4. **Attempt D1-07 transfer on Semaphore-Noir.** The selected target has
   different circuit structure (recursive batch proofs). Would test whether
   the pipeline works beyond Payy-style settlement, but the bb CLI is
   unpinned and the proving path is untested.

The roadmap says: "Continue beyond this gate only when the repaired controls,
concrete faulty case, baseline comparison, and transfer evidence support
further investment." Two of four conditions are not met (baseline comparison
shows no advantage; no transfer evidence). The honest conclusion is that D1
does not currently support the contribution and should either close or
substantially narrow.

## Assumptions and limitations

- **No new N=8 runs.** The solver scalability limit is established by D1-01.
- **No Payy consumer analysis.** The comparison uses the synthetic symbolic
  walk, not the real third-party consumer.
- **Synthetic only.** Real circuits may have different constraint structure
  that benefits selective refinement — but the solver must handle them first.
- **Single solver.** cvc5 1.4.2 GPL is the only solver tested. A different
  solver or theory combination might change the scalability picture.
