## 1. Outcome

BindCheck v1 is a working command-line tool:

```text
bindcheck analyze <producer artifact> <consumer source>
bindcheck validate <warning>
```

`analyze` emits readable diagnostics and a versioned JSON result containing
the location, rule, explanation, evidence, and suggested fix. The rule engine
contains no WarpToad, Payy, mutation, contract, or application identifier. It
decodes beta.14 or beta.22 ACIR, flattens the artifact ABI, counts
proof-enforced witness occurrences, and joins those roles to either a checked
consumer relation or a conservative source profile. Every target is analyzed
alone; no reference-version result is an analyzer input.

The five requested runs produce the expected separation:

| target | warnings | highest validation | static runtime | extra manual input |
|---|---|---:|---:|---:|
| WarpToad pinned | none | n/a | 1.534 s | checked D1P-18 relation path (1) |
| **INJECTED** M-DOM | `R-BIND` on public word 5 | fresh E4 | 1.565 s | relation path + validation adapter (2 total) |
| **INJECTED** M-SRC | `R-ANCHOR` on local root | fresh E4 | 1.476 s | relation path + validation adapter (2 total) |
| Payy earlier | `R-BIND`, `R-EFFECT` on tail words | preserved E4 | 0.035 s | historical candidate/adapter (2) |
| Payy check-added | none | n/a | 0.031 s | none beyond ordinary artifact/source arguments |

The two honest/repaired negative controls have **0/2 false warnings** in this
supported scope. This is not a general precision estimate. The three positive
targets are development cases already known to the project, not held-out
transfer. The two Payy warnings describe one concrete mismatch and therefore
reuse one E4 chain; they are not counted as two independent validated cases.

The final end-to-end runner completes all five analyses and four warning audits
in 4.661 seconds after proof evidence exists. Static timings are native-Mac
development observations, not performance results.

## 3. Static rules

The producer frontend selects the already separate beta.14 bincode or
beta.22 MessagePack decoder by exact `noir_version`. It rejects other
versions. It derives public witness identities from the ABI and counts only
decoded proof-enforced opcodes. Brillig remains witness-generation machinery;
its presence does not by itself discharge a binding.

With the required two positional arguments, the CLI first checks a
hash-pinned consumer-relation index. A match selects the prior checked
relation and records it as a manual input; absence falls back to the
conservative source profile. The index is orchestration data and is never
visible to the rule engine.

The v1 obligations are:

- **R-BIND:** a verifier argument constructed by the consumer must occur in
  the proof-enforced producer ACIR. Adjacent unused array leaves are grouped
  into one diagnostic.
- **R-ANCHOR:** an input classified as a root/anchor must have a positive
  must-be-in state check on every successful consumer path.
- **R-EFFECT:** public words decoded into an effect amount, beneficiary, or
  message must also be used by the proof-enforced producer.
- **R-POLARITY:** anchors are must-be-in. Replay keys are must-not-be-in in the
  pre-state and the same key must be written atomically on success. The latter
  is explicitly a two-transaction obligation.

R-BIND and R-EFFECT jointly implement the requested producer-use and
effect-dependency check: the former checks every constructed word; the latter
checks the consumer effect slice. An ACIR occurrence proves syntactic use, not
injectivity, cryptographic intent, full semantic dependence, or policy
correctness. In particular, Poseidon/recursive black boxes contribute checked
input/output occurrences but v1 does not infer collision resistance or
injectivity from them.

For WarpToad, the D1P-18/D1P-21B solc-AST relations provide public-word,
success-path, effect, state-write, and rollback roles. This relation path is a
counted manual input. For Payy, the conservative source profile locates the
verifier array, message dispatch, old-root state comparison, spent-key
polarity, and mint/burn effect functions. It reports the profile's limited
Solidity semantics in JSON.

## 4. Static results

### 4.1 WarpToad pinned

All eleven public witnesses occur in proof-enforced ACIR. Both root inputs
have positive history checks on every successful path. The nullifier is
required absent and written on success. Effect amount and beneficiaries are
derived from used public inputs. The supported scope emits no warning.

This is a clean development control, not a safety verdict: occurrence does
not establish all intended Poseidon/domain relations or the full protocol
policy.

### 4.2 M-DOM

The independently decoded M-DOM artifact has the same eleven public ABI
leaves, but witness 5, `aztec_warptoad_address`, has occurrence count zero.
The consumer nevertheless constructs verifier word 5 from stored
configuration. BindCheck emits:

```text
W001 R-BIND at m-dom-withdraw.json:abi.aztec_warptoad_address
```

This is derived from the artifact under test alone. The analyzer does not
compare M-DOM with pinned. D1P-21A separately explains that M-DOM uses private
witness 59 in the domain hash; that fact is supporting interpretation, not an
input to this warning.

### 4.3 M-SRC

All eleven pinned producer words remain used, but the M-SRC extracted
consumer relation has no positive state-membership guard for public word 4,
`destination_local_root`. BindCheck emits:

```text
W001 R-ANCHOR at WarpToadCore.sol:161
```

The giga-root must-be-in guard and nullifier must-not-be-in/write polarity
remain present.

### 4.4 Payy earlier and check-added

In the earlier beta.14 `agg_agg` artifact, `messages[0]` occurs twice but
`messages[1]` through `messages[7]` occur zero times. The consumer dispatches
the message array into mint/burn effects. BindCheck groups the seven unused
leaves into one R-BIND warning and emits one R-EFFECT warning at
`RollupV1.sol:397`.

In the check-added artifact all eight message witnesses occur in
proof-enforced constraints (`messages[0]` three times; the remaining seven
once each), so neither warning fires. The same source profile recovers the
old-root positive check and spent-key absent/write replay pair on both
targets.

The earlier and check-added artifacts were each analyzed independently. The
tool did not use a revision diff or the other target's outcome.

## 5. Validation

`bindcheck validate` selects a content-addressed route from the checked
[validation index](../protocols/d1/d1p-30-validation-index.json). Route
association is separate from and never consulted by static rules. Its manual
inputs are counted in every result. A clean namespace causes the two
WarpToad routes to run their fixture command automatically; an existing
D1P-30 sentinel is audited without regenerating another proof.

### 5.1 Fresh M-DOM E4

The first fixture launch generated its first proof and then failed to write
the new evidence because the D1P-30 output directory did not exist
(`ENOENT`). The unchanged corrective route created only that directory and
reran. This failure and reason are preserved.

The corrective run took 28.82 seconds, peaked at 737,181,696 resident bytes,
and generated two real 9,152-byte proofs: an honest control and the designated
foreign-contract note. For the foreign case:

- the note contract is distinct from the configured address;
- NoirJS executes the compiled M-DOM artifact;
- bb.js verifies the proof and the generated Solidity verifier accepts it;
- the unchanged local consumer accepts and writes the nullifier;
- recipient and total-supply deltas are each `5e18`, with zero relayer mint;
- the pinned producer rejects the same foreign semantic witness.

This reaches fresh **E4 for the injected M-DOM variant**. The task did not
have a standalone complete `Prover.toml`, so literal `nargo execute` was not
available; the route records that failure and uses the project's supported
NoirJS ACVM execution before proof generation.

The reused fixture contains a stale field named `ownVerifierRuntimeUsed` that
compares separately linked runtime bytecode and is false because freshly
deployed transcript/relation library addresses differ. D1P-15 already records
that expected link-address behavior. D1P-30 does not use this misleading
comparison as a gate; it checks mutation artifact identity, proof-system
verification, generated-verifier acceptance, and consumer state effects.

### 5.2 Fresh M-SRC E4

The M-SRC route took 98.99 seconds, peaked at 489,766,912 resident bytes, and
generated one real 9,152-byte proof. The giga root is admitted and the private
local root is not. NoirJS executes the pinned artifact; bb.js and the pinned
generated verifier accept; M-SRC accepts and commits a nullifier write plus
`3e18` recipient/supply deltas. This reaches fresh **E4 for the injected
M-SRC variant**. No cross-chain reachability is claimed.

### 5.3 Preserved Payy E4

No new Payy proof was generated. The validator automatically verifies the
exact preserved sequence:

1. T15's pinned Rust/ACVM harness constructs and satisfies the earlier
   recursive witness while the check-added circuit rejects it;
2. T16 propagates the record through `agg_final`, generates a real proof, and
   independently verifies it under the committed key;
3. T18 submits those exact bytes to the unchanged earlier consumer, observes
   its real token balance change `100 -> 93` and beneficiary `0 -> 7`, and
   checks that a second transaction reverts without changing state.

The highest level is **preserved E4**, explicitly not a fresh D1P-30 proof.
Literal `nargo execute` is unavailable because the complete recursive private
inputs are constructed by the pinned Rust harness rather than a standalone
`Prover.toml`; the alternative route and two historical manual inputs are
recorded. It requires the owned local prover and validator identities used by
the original experiment.

## 7. Limits and claim boundary

- This is development evidence. The positive cases were already exposed to
  the project and do not establish held-out transfer.
- No generic/default or same-policy baseline arm ran, so capability-gate part
  (c) remains open.
- The content-addressed validation association is a counted manual input. The
  tool does not yet synthesize a concrete witness from an arbitrary warning.
- The consumer source-only profile is bounded syntax recognition, not a full
  Solidity semantic extractor. The stronger WarpToad route uses prior checked
  AST relations.
- Public-witness occurrence is conservative. It can miss semantic weakness
  inside a used hash or recursive relation and can warn on deliberately
  unconstrained metadata. It establishes neither injectivity nor policy.
- No solver campaign, joint encoder, fork, live-chain action, maintainer
  contact, or held-out inspection ran.

D1P-30 demonstrates a working v1 analyzer and automatic, evidence-ordered
validation on development cases. It does not complete the four-part research
capability gate, establish automatic witness synthesis, prove general
precision/recall, or support a security verdict. D1 remains **UNKNOWN**.
