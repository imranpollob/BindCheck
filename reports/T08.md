## 4. Boundary (observed source behavior vs interpretation)

All paths at `dcd5d96`; line numbers from that revision.

**What the circuits establish (observed).** `noir/agg_agg/src/main.nr`: public inputs `verification_key_hash[2]`, `old_root`, `new_root`, `commit_hash`, `messages: pub [Field; 1000]` (l.14–22). It verifies two inner proofs and, per proof, walks that proof's messages; typed messages are compacted (kind 2 consumes 4 words, kinds 3/4 consume 5) and everything after the end must be zero (l.48–79). It then requires the outer `messages` to equal the exported messages up to `messages_index`. `assert_message_tail_zero(messages, messages_index)` (l.108, defined l.117) requires every outer message from `messages_index` on to be zero; `c4d2c90` has no such call (0 occurrences) and `dcd5d96`/`main` have it (4 occurrences incl. tests). `noir/agg_utxo/src/main.nr` has a tail-zero check in both revisions. `noir/agg_final/src/main.nr` forwards `old_root, new_root, commit_hash, messages` as public inputs of an UltraHonk proof of the `agg_agg` proof. Between the two revisions `agg_final` differs only in the constant `AGG_AGG_VERIFICATION_KEY_HASH` (observed diff), as expected when `agg_agg` changes.

**What the consumer receives.** `eth/contracts/rollup3/RollupV1.sol` `verifyRollup(height, verificationKeyHash, aggrProof, bytes32[] publicInputs, otherHashFromBlockHash, signatures)` (l.314), with `publicInputs = [oldRoot, newRoot, commitHash, messages…]`, length required to equal the registered `messages_length + 3` (l.330–332).

**What acceptance permits.** After the root check, validator-signature check and `onlyProver` gate (l.152), `verifyAllMessages` (l.349, l.384) decodes the messages from `publicInputs[3..]`: kind `0` is skipped; kind `2` (mint, `verifyMint` l.418) requires `mints[hash].amount == value`, matching `note_kind`, `spent == false`, then sets `spent = true` (l.435); kind `3` (burn, `verifyBurn` l.442) calls `executeBurn` to transfer `value` of the token for `note_kind` to `burn_addr` (l.466, `executeBurnToAddress` l.516); any other kind reverts (`"Invalid message kind"`, l.414). Then `verifier.verify(aggrProof, publicInputs)` must return true or the call reverts (l.357–361), and the root and height advance. Message effects execute **before** the verifier call within one transaction, so a reverting verification rolls them back.

**Correspondence that must hold (interpretation).**
1. *Consumer side:* every typed message in the authenticated `publicInputs` is dispatched exactly once with its decoded identity and amount (mint → pending `mints[hash]` consumed once; burn → transfer to `burn_addr`).
2. *Producer side:* every non-zero message in the public statement corresponds to a transaction actually processed by the aggregated proofs. The advisory's flaw is a violation of (2) in the circuit: tail slots of the outer `messages` were unconstrained, so a prover could append a forged burn after the real messages. The consumer then (correctly, by (1)) executes it.

**Consequence for BindCheck (interpretation).** The T01–T07 property is consumer-side coverage of the statement. For this advisory the consumer dispatches exactly what the public inputs say, so a consumer-trace checker would **not** flag the forged-tail execution by itself; detecting it needs producer-side facts (the circuit's constraint on the tail) combined with the consumer's behavior. That is the meaningful difference and also the main risk to a "second case of the same kind".

**Possible consumer-side observation (not a claim):** `verifyBurn` ignores `executeBurn`'s return value. A failed token transfer emits `Burned(…, success=false)` and does not revert, while the root advances. Whether this is intended policy (the whitepaper and the substitution mechanism may cover it) is unresolved.

**Conditions for GO:**
1. A real UltraHonk proof plus its public inputs that the real generated Honk verifier accepts in a local EVM test, either from the committed fixtures (provenance verified) or generated with the pinned `bb`. ## 8. Limitations

- The advisory and the Aztec report were read through a fetch tool's summarization; claims taken from them are *reported*, not confirmed. The guide earlier noted the advisory was unreadable; it was readable this time, which is itself unverified for completeness (PoC gist not accessed).
- Only three candidates were inspected and Tornado was surveyed, not built. Choosing Payy is a feasibility judgment, not a measurement of case yield.
- A synthetic mutation of this consumer, if made later, must be labeled synthetic. This report does not assert that the repository contains an exploitable consumer defect.
