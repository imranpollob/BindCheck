## 1. Result

**Completed within budget.** The unmodified upstream test `circuits::tests::test_agg_final` produced inner proofs and one new `agg_final` proof; the independent native verification (`bb verify`, repo flavor, committed `agg_final` key) succeeded, and a one-byte tampered public input was rejected. ## 2. Padding route (established from code)

Entry point: the upstream harness `pkg/zk-circuits/src/circuits/tests.rs::test_agg_final` (l.333–426), `utxo → agg_utxo → agg_agg → agg_final`, each step `prove_and_verify` through `CliBackend` (`pkg/barretenberg-cli`, which calls `bb prove/verify --scheme ultra_honk`, adding `--oracle_hash keccak` for the EVM circuit). Other candidates: `noir/recurse.sh` is a stale example (targets a `recursion` package and an old `--recursive` flag); `pkg/aggregator` `BlockProver` is the service path, not used.

**Padding does not bypass inner-proof verification** (code, `dcd5d96`):
- `noir/agg_utxo/src/main.nr`: `verify_proof_with_type` always runs ("will ALWAYS be run"); a padding slot (`utxo_kind == 0`) re-verifies slot 0's proof and public inputs, and slot 0 is asserted not to be padding ("first proof cannot be a padding proof"). So at least one real leaf `utxo` proof is mandatory.
- `noir/agg_agg/src/main.nr`: a padding proof (`old_root == 0`) is verified using `proofs[0]`'s proof and public inputs; if `proofs[0]` were padding the substituted bytes would have to verify, so the first aggregate proof must also be real.
- Rust `BlockProver::prove_chunk` returns a default (empty-bytes, zero-public-input) `AggUtxoProof` for a padding chunk; the circuit substitutes `proofs[0]` for such a slot rather than verifying those bytes (code reading; the service path was not run).

So "all-padding" cannot mean "no real proofs". In this run it means an all-zero message vector: two real `UtxoKind::Send` transfers (no mint or burn, hence no messages), each placed in its own `agg_utxo` chunk with two default padding bundles.

**Prerequisites in this route:** two leaf `utxo` proofs from synthetic notes in an in-test `smirk` tree (secret key 101); the four committed circuits and keys (`utxo`, `agg_utxo`, `agg_agg`, `agg_final`, embedded from `fixtures/circuits/`); the local `bb` CLI; the CRS (fetched by `bb` into `~/.bb-crs` on demand). No signatures, validator set, chain, database or external service. The Rust build needs crates.io plus the git dependencies (Noir `v1.0.0-beta.14`, and Payy's Aztec fork, fetched but its optional `bb_rs` binding unused).

## 3. Inner-key binding

**Established (mechanical, `10_inner_key_binding.txt`).** For both revisions, `bb write_vk` regenerates the committed `utxo`, `agg_utxo` and `agg_agg` keys byte-for-byte, and the vk hash it writes equals the hard-coded constant: `UTXO_VERIFICATION_KEY_HASH` in `agg_utxo` (`2036…1294`, same at both revisions); `AGG_UTXO_VERIFICATION_KEY_HASH` in `agg_final` (`5897…1812`, same at both); `AGG_AGG_VERIFICATION_KEY_HASH` in `agg_final` (`1162…4243` at `c4d2c90`, `5566…0105` at `dcd5d96`, each equal to that revision's `agg_agg` key hash).

**Code reading.** `agg_final` asserts its private `verification_key_hash` equals the `AGG_AGG` constant and passes `[AGG_UTXO, AGG_AGG]` as the inner proof's public `verification_key_hash[2]`. `agg_agg` is generic: each inner proof's own key hash must be one of those two public values, and that hash is passed to `verify_proof_with_type`. `agg_utxo` fixes the leaf key by its own constant.

**On "unchanged across revisions".** `agg_final`'s own key and Solidity verifier are *not* unchanged: they differ between revisions (T09) because the `AGG_AGG` constant changed. What is unchanged is the `AGG_UTXO` constant, plus the committed proof file and the stale `agg_agg.sol`. So the final artifact at `dcd5d96` is tied to the `dcd5d96` `agg_agg` key and, by the same logic, would not accept an `agg_agg` proof from `c4d2c90`; I did not test that.

**Uncertain.** That `verify_proof_with_type(vk, …, key_hash, …)` forces the supplied `vk` witness to hash to `key_hash` is Noir/bb semantics I did not examine in this repo; the binding argument depends on it. Also unexamined: whether a different valid circuit with the same vk hash could exist (cryptographic assumption), and the recursion proof-type argument `7`.

## 6. Deviations, failures, side effects

- **Attempt 1 failed (environment):** `librocksdb-sys 0.11.0+8.1.1` (via the dev-dependency `smirk`) did not compile: `fatal error: 'memory' file not found`. Plain `c++` on this machine does not search the SDK's libc++ headers (reproduced outside cargo). Workaround in `scripts/t10.sh`: `CXXFLAGS=-isystem $(xcrun --show-sdk-path)/usr/include/c++/v1`. Logs kept in `results/raw/T10/attempt1_cxx_headers_missing/`. No upstream file was changed.
- The repo's `.cargo/config.toml` (`--cfg tracing_unstable`, `ts-rs` dir) was mirrored via env, because cargo runs from the project root, not inside the checkout.
- The `bb` recorder is a pass-through: it executes the real pinned `bb` unchanged and only copies files (not a mock).
- Side effects outside the workspace: rustup auto-installed Rust 1.91.0 (triggered by `rustc --version` inside the checkout); cargo caches in `~/.cargo`; `~/.bb-crs` (256 MiB) created by the upstream test; `build/T09/crs` (a CRS cache, not a T09 artifact) grew from 64 MiB to 256 MiB during the vk-hash step. T09 results are unchanged.
- `scripts/t10.sh` ran once end to end after the workaround; the summary was regenerated once afterwards (a corrected note about the 1003 fields).
