## 3. Design (explicitly a test architecture, not a deposit protocol)
- `batchId = keccak256(abi.encode(all ten public inputs))`; deposit identity `(batchId, rowIndex)`. The T01 circuit has no deposit IDs, so this is a demonstration identity only.
- `fund(pubSignals[10], row)` payable: row < 4, row active (`pub[4+row]==1`), `msg.value == pub[row]`, not already funded. Stores `(amount, funded, consumed)`.
- `submit(pA,pB,pC,pub)` checks in this order: (1) `pub[8] == currentCommitment` else `OldCommitmentMismatch`; (2) real verifier accepts else `InvalidProof`; (3) for each active row, a funded entry (`MissingEscrow(row)`), not consumed (`AlreadyConsumed(row)`), stored amount equals `pub[row]` (`EscrowAmountMismatch`); marks consumed and adds to `consumedBacking`; (4) stores `pub[9]`. Any failure reverts the whole call, so consumption and the commitment update are atomic.
- ETH stays in the contract; consumption only reclassifies it (1 unit = 1 wei). No withdrawals or cancellation.

## 4. Invariant checked
For an accepted batch B with public amounts `a[i]` and flags `f[i]`: for every row i with `f[i]==1`, exactly one escrow entry `(batchId(B), i)` existed, was funded with exactly `a[i]` wei, and was unconsumed before settlement and consumed by it; rows with `f[i]==0` have no required entry; the commitment moves old → new only in the same transaction. Tests assert per-row (amount, funded, consumed), `consumedBacking`, ETH held and the commitment, with expected values taken from the T01 literals (`[100,250,0,40]`, `[1,1,0,1]`, credit 390) and an independently encoded `batchId`, not read back from the contract.

## 6. Assumptions, limitations, observations
- 6b needs a test-only harness because production code cannot reach "consumed entries with the old commitment stored". With only one proof, the consumption guard is otherwise unreachable.
- `EscrowAmountMismatch` is redundant today (`fund` already forces stored amount = public amount); it is kept as defence in depth and only appeared when the funded check was removed.
- Funding is permissionless and unauthenticated: any caller can fund any claimed batch, and the batch is not proof-checked at funding. ETH funded to a never-proven batch stays locked (no refunds). There are no depositor identities, nullifiers or authorization.
- **Privacy:** all ten public inputs (amounts, flags, both commitments) are public calldata; funding transactions reveal row amounts. The commitments are unsalted Poseidon of low-entropy balances, so balances are brute-forceable. No confidentiality is claimed.
- **Setup:** the T01 Groth16 setup is a toy with public, recomputable entropy; anyone could forge proofs for this key. These tests show integration and the honest path, not adversarial soundness.
- **Open question (not investigated in T03):** the T02 observation that an off-curve proof point makes the generated verifier burn ~1.07B gas in the test EVM (precompile failure consumes forwarded gas) and return `false`. It still appears in the T02 test output here.
- Not run: fresh-machine rehearsal, fuzz/invariant testing, multiple batches per consumer, funding after settlement, Hardhat.
