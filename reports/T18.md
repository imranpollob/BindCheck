# T18 — Does the T16 synthetic burn record produce a token transfer on a locally deployed earlier-revision consumer?

Authorized defensive academic research; locally deployed contracts, owned test accounts (prover, validator, minter), Foundry's local EVM. Earlier Payy revision **only**, matching T15/T16's "A": `c4d2c9021b8fb9988816eb6987a734b830bfce15`. **Reuses T16's exact control and candidate `agg_final` proof and public-input bytes — no new proof, no circuit or verifying-key change.** Both calls below use whitelisted prover/validator identities we created and control ourselves; this is a local result for that revision and those test identities, not a claim about an arbitrary attacker or any historical deployment.
Reproduce: `bash scripts/t18.sh` (about a minute; no proving). Evidence: `results/raw/T18/` (`00_environment.txt`, `50_forge.log`, `51_forge_results.txt`, `observations/*.json`, `90_summary.json`); test source `payy-consumer/test/BurnPropagation.t.sol`.

**Funding, and why it is not a separate/artificial step.** Both proofs' shared mint record (indices 3–6, value 100) must be registered for either call to settle at all — an unregistered mint reverts at `verifyMint` before the burn record is ever reached (T17, confirmed again below). Registering it through the **normal, documented path** (`token.approve` + `RollupV1.mint(hash, 100, noteKind)`, exactly as T13) **escrows exactly 100 units into the consumer**, which already exceeds the burn's 7 units. No separate "fund the consumer" step was added; the consumer's balance comes entirely from the registration every case already requires. **What this means for an "insufficient balance" control:** because this fixed proof's mint value (100) always exceeds its burn value (7), a case of "mint properly registered, but balance too low for the burn" is **not reachable without a new proof** — see §4 for the alternative actually run.

**Signature coverage, recorded as data.** `RollupV1.getSignatureMessageHash` is a pure function of `(newRoot, height, otherHashFromBlockHash)` only (confirmed in T17). The control and candidate share the same `newRoot`; a signature was computed once per call and — separately — verified bit-identical and interchangeable in §4.

## 2. Calls and results

Each case below is a freshly deployed `TransparentUpgradeableProxy` over the same `RollupV1` implementation and the same linked verifier (both stateless; sharing them changes nothing about what a given instance checks or holds), same owned prover/validator/minter addresses, same note-kind→token mapping.

| # | Case | Result | Verifier reached? | Burned event | Token balanceOf check |
|---|---|---|---|---|---|
| 1 | **Baseline**: mint-only control, registered, submitted | accepted, 4,296,193 gas | yes, exact calldata | not emitted (no burn message) | rollup balance unchanged (100→100) |
| 2 | **Candidate**, mint registered (normal path), submitted | accepted, 4,322,830 gas | yes, exact calldata | emitted, **`success = true`** | **rollup 100→93, burn_addr 0→7** — independently confirmed via `balanceOf`, not inferred from the event |
| 3 | Candidate, **no mint registration / no funding** | reverted | no | not emitted | unchanged (`_assertSame`) |
| 4 | Candidate **resubmitted** on the instance from #2, after it already settled | reverted | no | not emitted | unchanged from right after #2 |
| 5 | Signature-reuse check (not a settlement outcome) | both calls accepted | — | — | confirms sig bytes are interchangeable |

All 5 Foundry tests pass (`51_forge_results.txt`). Machine/toolchain as in T15–T17.

**Case 1 (baseline).** Confirms this locally deployed revision-A consumer and verifier function correctly end to end before any burn is involved: root advances to the proof's `new_root`, the mint settles (`spent` set), no balance changes (mint settlement moves no tokens, as established in T13).

**Case 2 (the test).** The candidate settles. `Minted` fires for the mint record (same block, same as case 1), then a real ERC20 `Transfer(rollup → 0x…dead, 7)` event from the **token contract itself** (not the consumer), then `Burned(token, hash, 0x…dead, substitute=false, success=true)`, then `RollupVerified`. **Checked independently of the event:** `token.balanceOf(address(rollup))` dropped by exactly 7 and `token.balanceOf(0x…dead)` rose by exactly 7 (`pre`/`post` in `2_candidate_funded_burn_executes.json`). The `Burned.success` field and the real balance change agree here, but the check was made on the balances, not the event, per the task's instruction.

**Case 3 (blocking check, identified precisely).** Rejecting check: `"RollupV1: Mint value invalid"` — the mint record (indices 3–6), processed before the burn record in `verifyAllMessages`'s sequential walk, fails first because `mints[hash].amount == 0 ≠ 100`. The verifier is never reached and the burn record is never evaluated. This is the same check T13/T14 already established for an unregistered mint; it is not specific to the burn.

**Case 4 (atomicity).** A second submission of the identical candidate on the same (now-settled) instance reverts with `"RollupV1: Root hash verification failed"` (the proof's `old_root` no longer equals the instance's `rootHash`), and every piece of tracked state (root, height, mint entry, all four tracked balances, registry) is unchanged from immediately after case 2.

**Case 5 (signature coverage, demonstrated).** One signature computed for the control's `(newRoot, height, otherHash)` and one for the candidate's came out byte-identical (`r`, `s`, `v` all equal — expected, since both proofs share the same `newRoot`/`height`/`otherHash` and the hash function takes no other input). Each signature was then used, **swapped**, to submit the *other* proof to a fresh instance, and both settled — confirming the bytes are not merely equal but functionally interchangeable between these two otherwise-unrelated calls.

## 3. Property verdict

**Property under test:** a burn effect accepted by the consumer must be justified by a burn represented in the circuit-authorized inner transactions.

**Result: the property is violated by this local experiment**, under the stated authorization assumptions (owned prover + owned validator quorum, no bypass of any contract check). Case 2 is a token transfer whose amount, recipient, and existence trace only to a message word that T15 showed is unconstrained by the earlier revision's `agg_agg` circuit and T16 showed propagates unexamined through `agg_final` — not to any burn-kind UTXO proof with an owned, balanced input note. The transfer is real (checked by `balanceOf`, not by the event alone), the call did not revert, and no parser or verifier rejection occurred.

This verdict is scoped exactly as the setup is: the **earlier** revision, **owned** local prover and validator identities (not an arbitrary unauthorized user, and not evidence that any real validator quorum ever signed anything like this), and a synthetic message with no backing note. Cases 3 and 4 show the same consumer does reject the obvious adjacent cases (no registration; replay) without any special handling — the violation in case 2 is specific to the unconstrained tail word, not a general weakness of the checks that are present.

## 4. Alternatives tried before accepting the blocker in case 3's class of test

The task asked for up to three reasonable, source-supported alternatives before reporting a blocker. The only blocked path encountered was the "registered mint, but balance insufficient for the burn" sub-case; alternatives considered, without changing the proof or bypassing any check:
1. **Direct funding of the consumer, bypassing `mint()`.** Rejected: this fixed proof's registration already deposits 100 (≥7) as a side effect of a check the call requires anyway (§1); adding a separate, smaller top-up would not reduce the pre-existing 100, so it cannot produce "registered but insufficient" without removing or shrinking that escrow.
2. **Leaving `tokens[note_kind]` unset to simulate a zero balance.** Rejected: `RollupV1.mint()` itself requires `tokens[note_kind] != address(0)` (source-confirmed), so an unset token mapping blocks the mint registration itself, not specifically the burn — this collapses into case 3's already-covered result, not a new one.
3. **Draining the escrowed balance after registration via some owner/prover function.** Rejected: no such function exists in this source (no sweep/withdraw path was found in T17's trace); inventing one would be a consumer change, which the task forbids.

**Conclusion for this sub-case:** a true "mint registered, burn underfunded" control is **not reachable with this exact proof** — reaching it would require a new proof with a mint value smaller than the burn value (a proof-bound field), which was explicitly out of scope. Case 3 (no registration at all) is reported instead as the nearest reachable, zero-new-proof control, and it is a different, already-expected rejection (the mint check, not a burn-balance check).

## 5. Limitations

- One synthetic burn of 7 raw units, one note kind, one validator, a local ERC20. No burn substitution path exercised (`substitutedBurns` was empty in every case; the direct-payout branch of `verifyBurn` was the one taken).
- The implementation and verifier contracts were shared, byte-for-byte, across all deployed instances (both are stateless logic with no consumer-specific storage); only the proxy, its storage, and its own token instance are fresh per case.
- This is not a claim that any ordinary, unauthorized user could produce case 2's effect: both the prover and the validator quorum are addresses we created and control in this testbed; off-chain validator diligence (T17, unresolved) is outside any of this.
- Not run: the substitutor reimbursement path; multiple burns in one block; any live or historical deployment; the later (fixed) revision (already shown in T15 to reject this exact witness before any proof exists, so no consumer-level test is possible there with this candidate).

**Smallest next step (T19):** none proposed beyond what T17 already scoped; this task completes that scope. If further work is wanted, the next natural step would be to test whether the `substitutedBurns` path is also reachable by an untraced burn record (a pre-registered substitutor paid out against a hash that was never behind a real burn), which would need its own, separately scoped setup.
