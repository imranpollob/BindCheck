# T13 — One proof with a single mint message, settled through Payy's real local consumer

Authorized defensive academic research on a local testbed (local contracts, owned test accounts, Foundry's local EVM, locally generated proof). Revision `dcd5d96ee15664a59bc24ed0dc2bb78b73ac5e36`; pinned `bb 3.0.0-manual.20251030`; Rust 1.91.0; Foundry 1.4.1.
**This demonstrates one local effectful execution. It does not reproduce the advisory, establish a vulnerability, or show that BindCheck detects one.**

Reproduce: `bash scripts/t13.sh` (reuses the generated proof; `T13_FORCE=1` regenerates it, about a minute). Evidence: `results/raw/T13/` (`10_mint_path_evidence.txt`, `40_proof_summary.json`, `90_summary.json`, `observations/*.json`, `agg_final_mint/`).

## 1. Mint path (traced before generating)

**Circuit-enforced** (`noir/utxo/src/main.nr` mint branch; `noir/agg_utxo/src/main.nr`; `noir/agg_agg/src/main.nr`; line numbers in `10_mint_path_evidence.txt`):
- A mint message is four words `[kind=2, note_kind, value, mint_hash]` placed from index 0 of the 1000-word `messages` vector, followed by zeros (`agg_utxo` copies them and advances 4; `agg_agg` compaction treats kind 2 as a 4-word record; the tail-zero check covers the rest).
- `output_value == input_value + value` (the minted amount is exactly what the output notes add), `value ≤ 2^240`, `output_notes[0].kind == note_kind`, and `mint_hash == Poseidon2(output_notes[0].psi, output_notes[1].psi)` (the circuit comment explains the private `psi` values prevent front-running the hash). The note commitments are inserted into the tree between `old_root` and `new_root`.
- Not enforced by any circuit: that anyone paid for the mint, that a registration exists, which token a note kind means, or who the recipient is (the recipient is only inside the private note commitment; the message has no recipient field).

**Consumer assumptions** (`rollup3/RollupV1.sol`): `mint(mint_hash, value, note_kind)` is callable by anyone; it needs `tokens[note_kind] != 0`, pulls `value` of that token from `msg.sender` with `safeTransferFrom` (so an ERC20 approval is required), and records `mints[hash] = {note_kind, amount, spent=false}` with event `MintAdded`. During `verifyRollup`, `verifyMint` requires `mints[hash].amount == value`, `mints[hash].note_kind == note_kind` and `!spent`, then sets `spent = true` and emits `Minted`; it moves no tokens at settlement (the tokens were escrowed at registration). `tokens[note_kind]` is set by `initialize(…, initialNoteKind)` or the owner's `addToken`.

**Source discrepancy noted:** the contract comment says "Mint hash is hash of commitments", but the circuit hashes the two output `psi` values. I follow the circuit.

**Other facts relevant to setup.** A block that starts from an empty tree has `old_root` = the empty-tree root, which equals the root `initialize` hard-codes (`0x0577…79ff`; also `pkg/contracts/src/empty_merkle_tree_root_hash.txt`). So, unlike T12, **no `setRoot` is needed**. `verifyMint` does not reject a zero hash or zero value; T12's reaching-the-verifier control relied on that. Not explored further here.

## 2. Proof generation

Route: the upstream T10 route (`CliBackend` driving the pinned `bb`), with a small new harness `payy-harness/t13_mint.rs`, installed by the script as one new **untracked** file `pkg/zk-circuits/tests/t13_mint.rs` in the checkout (no upstream file edited; the checkout's only change is that file). It reuses upstream's helper logic: one `UtxoKind::Mint` utxo (inputs: padding notes; output 0: value 100, psi 1; output 1: padding), `agg_utxo` with 1 real bundle + 2 default padding bundles, `agg_agg` with 1 real `agg_utxo` + 1 padding proof built as `block_prover/prove.rs::padding_proof()`, then `agg_final`. The upstream test `test_agg_final_with_mint_and_burn` was not used because it carries a mint *and* a burn.

## 3. Settlement (actual consumer behind a `TransparentUpgradeableProxy`, actual verifier)

Local pattern as T12: solc 0.8.20 via-IR/200 consumer, OpenZeppelin 5.0.1 (lockfile-checked), verifier and `ZKTranscriptLib` from Payy's committed `.bin` files linked as `deploy.ts` does (T11's compiled-bytecode match holds only after excluding the library-address slot and metadata), executed on Cancun. One validator with an owned key signs the digest the consumer itself exposes; `initialize` is called with `initialNoteKind` = the mint's note kind, registry key as in T12. A local `MintTestToken` is the mapped token. Registration uses the normal interface (minter approves, then `mint(hash, 100, noteKind)`).

| Step | Observed |
|---|---|
| Registration | minter 1000 → 900, consumer 0 → 100; logs: token `Transfer`, then `MintAdded(hash, 100, noteKind)`; `mints[hash] = (noteKind, 100, unspent)`; gas 75,292 |
| `verifyRollup` (prover, height 1) | **success, 4,299,087 gas**; the real verifier is called with exactly `(proof, publicInputs)`, not reverted |
| Root / height | `0x0577b5b4…` → `0x17999024…` (the proof's new root); 0 → 1 |
| Mint state | `spent` false → **true**; amount and note kind unchanged |
| Token balances at settlement | unchanged (consumer 100, minter 900, prover 0, owner 0): no transfer happens when the mint is consumed |
| Events at settlement | exactly two, in order: `Minted(hash, 100, noteKind)` then `RollupVerified(1, newRoot)`; nothing from the token |

## 4. Controls (fresh equivalent deployments; protected state compared before/after: root, height, mint entry, all token balances, registry entry)

| Control | Result | Rejecting check | Verifier reached? |
|---|---|---|---|
| Encoded mint amount 100 → 101, original proof, the original 100-unit registration in place | reverted, 21,431 gas, state unchanged | `RollupV1: Mint value invalid` (`verifyMint`) | **No** |
| *Additional:* same altered amount, but a 101-unit mint is registered so the consumer's own checks pass | reverted, 2,079,441 gas, state unchanged (spent flag rolled back) | the real verifier, `SumcheckFailed()` | **Yes**, exact altered calldata |
| Encoded mint hash changed (the only identity in the message; there is no recipient field, so this stands in for "recipient"), original registration in place | reverted, 21,431 gas, state unchanged; the altered hash's entry untouched | `RollupV1: Mint value invalid` (altered hash unregistered, amount 0 ≠ 100) | **No** |
| Registration omitted, original proof | reverted, 21,430 gas, state unchanged | `RollupV1: Mint value invalid` (amount 0 ≠ 100) | **No** |

Execution order in `verifyRollup` (source): prover check, verifier lookup and length check, root check, validator signatures, message dispatch, verifier call. In the three consumer-rejected controls the signature (over `newRoot`, `height`, `otherHash`, which the altered fields do not change) is valid, so the rejection is the observed message check. Only the additional control exercises the verifier. Caveat for later checker work: Foundry's log recorder lists events emitted inside reverted frames (the additional control shows a `Minted` log that a chain discards); observations carry a note.

## 5. Limitations

- One mint of 100 raw units, one validator, a local ERC20 (not USDC), no burn, no multi-message block. Two registration-gas figures appear (75,292 in the main test, 92,392 in controls); I did not investigate the difference.
- The mint registrant need not be the note owner; the consumer cannot tell. Cross-key rejection of this proof was not tested.
- Proof bytes are randomized per generation; the public inputs were identical across two generations.
- Not run: effectful messages beyond a single mint, burn settlement, multiple validators, a non-prover caller, bad signatures.

**Blockers:** none. **Smallest next research task (T14):** write the manual spec and record mapping for Payy mint obligations (public-input positions 3 to 6, identity = mint hash, the registered-and-unspent → spent transition, escrow = registered amount) and evaluate these five executions with a direct Foundry assertion first; only if that is sound, decide whether the trace checker needs a message-grammar extension, as T08 anticipated.
