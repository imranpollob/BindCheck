# T20 — Classifying the Payy result against the official advisory

Authorized defensive academic research; desk analysis only. **No new transactions, no new proofs.** Source: the official GitHub advisory [GHSA-fhxc-63vg-9gwr](https://github.com/polybase/payy/security/advisories/GHSA-fhxc-63vg-9gwr) / CVE-2026-48100, fetched directly from GitHub's security-advisories API (public, unauthenticated; `results/raw/T20/10_advisory_api_response.json`), and T08–T19's existing reports and artifacts (not regenerated). Git evidence from `tools/cases/payy-history` is in `results/raw/T20/20_revision_mapping.txt`.

## 1. Advisory vs. our experiments: what is the same

| Advisory element | Our independent evidence | Match |
|---|---|---|
| Root cause: `agg_agg` forwards messages but never zero-checks the outer tail, while `agg_utxo` already does | T15 (source reading of both files, both revisions) + the replayed differential (candidate witness satisfiable at the pre-fix circuit, rejected at the fixed one) | **confirmed independently** |
| Exact rejecting assertion after the fix: `"Message is not zero"` | T15 §3 / T19 §1, byte-identical error text and circuit call stack, from our own separately-run harness | **confirmed independently** |
| Validator signature covers only `(newRoot, height, otherHashFromBlockHash)`, not `messages` | T17 §1/§3 (source trace) + T18 case 5 (same `(v,r,s)` bytes settle both a legitimate and a forged-tail proof) | **confirmed independently**, including by actually exercising it, which the advisory's own write-up describes but does not itself demonstrate with a swapped signature |
| Consumer dispatch: a forged tail record is parsed as an ordinary mint/burn by `verifyAllMessages`/`verifyBurn`, no registration check on burns | T17 §1/§3 (source trace) + T18 case 2 (settles; `balanceOf` confirms a real transfer) | **confirmed independently** |
| `verificationKeyHash` for the affected `agg_final` circuit: `0x122d2ac7542fa020cbfff0836b5d0c30898330074b19869179bba49b5db69967` | Derived independently in T12 from Payy's own `vk_hash` binary over the committed `key_fields.json`, **before** this task read the advisory's PoC transcript closely enough to notice the match | **byte-identical** — strong convergent evidence we are examining the same artifact the advisory describes |
| PoC construction: real mint prefix + injected burn tail, same note kind, local test funding, local `RollupV1`, registered local "attacker" prover, unmodified validator approval | T15/T16 (same construction: mint prefix + burn-shaped tail) → T18 (local `RollupV1`, owned prover/validator, local ERC20) | **same shape**, smaller/different concrete values by choice (see §1 limitations) |
| Suggested mitigation: `assert(messages[i] == 0, "Message is not zero")` after the aggregation loop, before `commit_hash` | Matches the semantics of the actually shipped `assert_message_tail_zero` (T15) | **same effect** |

**What differs, precisely.**
- *Values, not mechanism.* The advisory's PoC uses `hash = 0`, an unspecified `attacker` address, and a burn value set to the rollup's full live balance; our T15/T16/T18 candidate uses `hash = 424242`, `burn_addr = 0x…dEaD`, and a burn value of 7 against a locally funded balance of 100 — deliberately small and synthetic, consistent with the standing constraint against reproducing the advisory's own scenario or its financial-loss framing.
- *The shipped fix is not literally the advisory's suggested diff.* The advisory's suggested patch is an inline loop placed directly in `main()`, and its own "mitigation was verified" transcript cites line `noir/agg_agg/src/main.nr:109:20` from a **temporary checkout with that inline diff applied** — not the commit Payy actually shipped. The commit we tested (`dcd5d96`) instead factors the same check into a named function `assert_message_tail_zero` (called from line 108, assertion at line 120) with two accompanying Noir unit tests. Same effect, different code shape; T15/T19 tested the actual shipped commit, not a reconstruction of the advisory's own suggested diff.
- *Scope of consumer-level testing.* The advisory describes the attack narratively and includes a PoC transcript; it does not, in the published text, show a signature-interchangeability test like T18's case 5, nor an explicit `balanceOf`-only verification methodology (it does print before/after balances, which T18 also does independently).

**Conclusion on mapping:** the **fixed** side maps cleanly — `dcd5d96` is the commit that adds the cited check, is tagged `beam-v0.1.0` in this mirror, and the fix persists unchanged to `HEAD` (`origin/main`, `beam-v0.3.0`), confirmed by re-reading `noir/agg_agg/src/main.nr` at `origin/main`. The **affected-version label does not map** to the vulnerable code we tested: `zk-circuits-v1.1.12` is a genuine, distant ancestor (same lineage, not a disconnected fork) but predates the Noir/`rollup3` codebase entirely — the bug did not exist at that tag because the vulnerable code did not yet exist. The **patched-version label** (`payy v1.3.0`) **cannot be established** against this mirror's tags or metadata; this is reported as unresolved, not assumed. This repeats and now evidences in full detail what T08 flagged earlier as an open discrepancy (T08 §3).

## 3. Current status of the claim

- **Known vulnerability.** Publicly disclosed, critical severity, `CWE-349` (Acceptance of Extraneous Untrusted Data With Trusted Data), `CVE-2026-48100`, published 2026-06-10, with a named reporter, a committed suggested fix, and a PoC description. This is **not a new discovery**; T08 selected this case specifically because it was already public.
- **Local reproduction (ours, independent of the advisory's own PoC code).** T15 (circuit-level: the tail is unconstrained pre-fix), T16 (propagates through `agg_final`), T18 (produces a real, `balanceOf`-confirmed token transfer through a locally deployed real consumer, under owned prover/validator identities) together reproduce the advisory's described mechanism end to end, using our own harness and test code, not the advisory's attached gist.
- **Repair check.** T19 confirms the shipped fix (`dcd5d96`) blocks our exact local candidate at circuit witness generation — the earliest possible point — while the legitimate mint path continues to settle normally and moves nothing to a burn address.
- **Unresolved: deployment/version attribution.** Whether the unfixed code was ever live on any network, when (if ever) the fix was deployed there, and how this mirror's tags relate to the advisory's version labels, are **not established** by this project. The advisory's own "live state check, 2026-05-05" (a mainnet `cast call` transcript) is the only evidence of any live deployment anywhere in this record, and it was not independently verified here — no live network was queried, per the standing constraint.

## 4. Contribution to the research: benchmark value and what would be needed for more

**What this case contributes as a development benchmark.** It is a real, disclosed, critical circuit-soundness bug with: (a) a genuine "before" and "after" circuit pair sharing the same consumer source, (b) a committed, public fix whose effect is mechanically testable offline, (c) a full local pipeline — proof generation, recursive aggregation, a real Solidity verifier, a real consumer, owned-authorization settlement — that needs no live chain and no mocks (T09–T19). Unlike the earlier toy batch fixture (T01–T07), the property here is grounded in an actual advisory with independent, mechanically checked corroboration (the matching verification-key hash, T15/T19's exact replay of the cited assertion). As a benchmark, it gives a proof-to-execution-binding tool two concrete targets: detect the missing tail constraint from the circuit alone, and/or detect that the consumer's burn dispatch has no registration analogous to mint's — the second of which (T17) is a reusable finding independent of this specific advisory.

**What this does not yet contribute.** T08 already noted, and this project has not since changed, that a purely consumer-trace-based checker would **not** flag this: `verifyAllMessages` correctly dispatches exactly what the public inputs contain; the violated invariant lives in the circuit's own witness structure (what the compacted inner proofs actually export vs. what the outer array exposes), which is producer-side, not consumer-side. T14 separately found that, under the current hand-written manual specification, BindCheck's checker and a direct Foundry assertion are functionally equivalent — i.e., *this project has not yet built or tested anything that would have caught this bug before the advisory existed.*

**What would be needed for a contribution beyond reproduction:**
1. A method that extracts the "active vs. padding" boundary (the invariant the fix enforces) **from the circuit source or ACIR itself**, rather than from a human reading the advisory and the diff — otherwise the "detection" is hindsight pattern-matching on an already-published fix, not a demonstrated capability.
2. Evidence that such a method generalizes: e.g., checking the *sibling* circuit (`agg_utxo`), which already has the correct check, to confirm the method reports "satisfied" there and "missing" in the pre-fix `agg_agg` — a same-codebase positive/negative pair, not just the one known-negative case.
3. A held-out case: applying the same method to an aggregation-style circuit whose soundness status is not already publicly known, to test whether it finds something *before* an advisory exists, not after.
4. A measured cost comparison (onboarding effort, lines of specification, time) between writing this property from scratch here versus adapting the T01–T07 batch-fixture specification — T08 flagged this as relevant and it remains undone.
5. If the paper wants to speak to real-world impact, independent verification of the advisory's live-state claims (which this project's standing constraints explicitly exclude) — absent that, any impact claim must stay scoped to "as reported in the advisory," not asserted by this project.

## Conclusion

This is a **known, publicly disclosed** vulnerability, not a discovery by this project. Our local, independently built reproduction (T15–T18) and repair check (T19) **corroborate** the advisory's described mechanism in detail, down to a byte-identical verification-key hash obtained through an unrelated derivation path, and identify one precise inaccuracy in a naive version-label reading (the advisory's cited affected tag predates the vulnerable code; the cited patched-version string does not resolve to anything in this mirror and the one superficial string match actively contradicts a version-marker reading). As a development benchmark this case is valuable for its realism and its independently checkable ground truth; it is not, by itself, evidence that any method developed in this project can find an *unknown* instance of this bug class. No real-world or live-deployment impact is claimed beyond what the advisory itself reports, and that report was not independently verified here.
