## 2. Verifier interface (source locations)

Verifier: Payy `eth/noir/agg_final.sol` @ `dcd5d96`, SHA-256 `c749ed63e283b066cd2f54baffb80f7febae062c8d4579ff8bf492f1873ebc1a`, byte-identical to `bb write_solidity_verifier` from the committed key (T09). Line numbers below refer to that file.

- **Call:** `verify(bytes proof, bytes32[] publicInputs) returns (bool)` (l.1928; interface l.135). `HonkVerifier` is constructed with `N = 2^20`, `LOG_N = 20`, `VK_HASH`, `NUMBER_OF_PUBLIC_INPUTS = 1019` (l.5–8, l.2431).
- **Proof bytes:** `proof.length` must equal `calculateProofSize(20) * 32` (l.1900, check l.1938). With `ZK_BATCHED_RELATION_PARTIAL_LENGTH = 9`, `NUMBER_OF_ENTITIES = 41`, `PAIRING_POINTS_SIZE = 16` this is 330 fields = **10,560 bytes**, exactly the T10 file (script recomputes it).
- **Public inputs:** `publicInputs.length` must equal `vk.publicInputsSize − PAIRING_POINTS_SIZE` (l.1945) = 1019 − 16 = **1003** `bytes32` words.
- **The 1019 vs 1003:** the key header's 1019 counts the circuit's public inputs including the 16-field **pairing-point object** produced by the recursive verification inside the circuit. Those 16 values are not in the public-input array. `loadProof` reads them as the **first 16 field elements of the proof bytes** (l.739–746; all 16 are non-zero in the T10 proof). They are then (a) hashed into the Fiat–Shamir transcript right after the 1003 public inputs (l.540–544), (b) included in the public-input delta (l.1954, `computePublicInputDelta`), and (c) folded into the final pairing check via `generateRecursionSeparator` / `convertPairingPointsToG1(proof.pairingPointObject)` (l.1685, l.2318–2320). The proof length formula includes them (`+ PAIRING_POINTS_SIZE`, "pairing inputs carried on public inputs").
- **Upstream serialization (pinned Rust):** `pkg/zk-circuits/src/circuits/proof.rs:72–90` splits raw `bb` output as the first `FIELD_COUNT × 32` bytes = public inputs and the rest = proof, with `FIELD_COUNT = 3 + 1000` taken from the circuit ABI (T10 decoded the ABI order); `pkg/zk-primitives/src/agg_final.rs:73–81` writes `old_root, new_root, commit_hash, messages` as big-endian 32-byte words; `pkg/zk-circuits/src/circuits/agg_final.rs:63` sets `kzg: vec![]`; `pkg/contracts/src/rollup.rs:453–469` calls `verifyRollup` with the proof bytes and `[old_root, new_root, commit_hash, messages…, kzg…]` as `bytes32` (empty `kzg`); the consumer requires `publicInputs.length == messages_length + 3` and calls `verifier.verify(aggrProof, publicInputs)` (`rollup3/RollupV1.sol:330, 357`).

**Conversion applied: none.** The `proof` file is passed unchanged; the `public_inputs` file is read as 1003 consecutive big-endian 32-byte words (exactly what the Rust code produces and what `bb` wrote). Nothing was padded, truncated or re-offset. The negative test changes only index 3: `0 old_root, 1 new_root, 2 commit_hash, 3 messages[0]`.

1. **Cross-revision artifact equality.** T09 reported each link per revision correctly, but its sentence that the proof file is byte-identical at both revisions could be read as "the final artifacts did not change". They did: the `agg_final` key and Solidity verifier differ between the two revisions (above) because the `AGG_AGG` constant inside `agg_final` changed. Only the `agg_utxo`/`utxo` keys, the stale `agg_agg.sol` and the old proof file are equal across revisions. The T10 proof is valid only against the `dcd5d96` `agg_final` key/verifier.
2. **Public-input count.** T09 noted the 1003 + 16 split only as an interpretation, stated that the key declares 1019 public inputs, and used a 1019 × 32-byte zero placeholder as if that were the public-input file size. The accurate statement: the *array* passed to `bb` (`-i`) and to `verify()` is **1003** fields; 1019 is the key-header count and includes the 16 pairing-point values carried in the first 512 bytes of the proof. Re-running the T09 diagnostic with the correct 1003 × 32 placeholder gives the same result: `Assertion failed: (val.on_curve())` at both revisions (`21_diag_old_proof_1003_placeholder_*.log`), i.e. the committed `.proof` still fails at proof deserialization, so T09's conclusion stands. The T10 interpretation "16 pairing-point inputs inside the proof" is now established by source (above) and by the verifier accepting the file.
3. **"All-padding".** In T10 it meant an **all-zero message vector** (1000 zero fields), not an absence of real proofs: the pipeline ran 2 real `utxo` proofs, 2 `agg_utxo` (each with 1 real bundle and 2 default padding bundles), 1 `agg_agg`, 1 `agg_final`; and `old_root` (`0x12e4daae…`) ≠ `new_root` (`0x06cd6fd0…`), so state changed. T09 called the old Halo2-era file an "empty/padding block" because all six decoded (hash, value) slots were zero; that over-claims, since transfers produce no mint/burn message. The supportable statement is only "no non-zero mint/burn values in the decoded slots under the Halo2-era layout".

## 5. Observations outside this task's question

- Two different verification-key hash values exist for `agg_final`: the verifier's own `VK_HASH` `0x0f8581a9…3328` (equals `bb`'s vk hash of the key), and Payy's Rust/registry constant `AGG_FINAL_VERIFICATION_KEY_HASH` `0x0701c58c…787c` in `rollup.rs` (and, at `c4d2c90`, `0x122d2ac7…9967` vs `bb` hash `0x016b9de0…a0dc`). Both revisions show the same pattern. How the Rust constant is derived is not determined here (the generator runs its own `vk_hash` binary on `key_fields.json`); `verify()` does not take it. It matters for the consumer's `verificationKeyHash` registry in the next step.
- The upstream interface declares `verify` as non-view while the implementation is `view`; calling it as `view` from Foundry worked.

## 6. Limitations

- One synthetic zero-message block; no mint/burn, signatures, validator set, consumer or storage effects.
- Not run: `verifyRollup`/`RollupV1` settlement, a proof with effectful messages, the Halo2-era verifier, a different EVM version or chain.
- The negative case is a single altered field; it shows the verification path is live, not any soundness property.

**Blocker:** none. **Next step (T12 proposal):** deploy `rollup3/RollupV1` with this verifier registered under the registry key it expects, and drive `verifyRollup` with the T10 zero-message proof (needs a validator set and signatures, and resolution of the `verificationKeyHash` discrepancy above); then plan effectful-message proof generation as a separate task.
