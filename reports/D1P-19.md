## 2. Current and proposed hash treatment

### 2.1 L0: current encoder

The current `joint_warptoad.py` encoding retains the decoded beta.22
arithmetic/range constraints, including all compiler-lowered BN254 Poseidon
arithmetic. Each of the 86 `Poseidon2Permutation` opcodes declares four output
witnesses but emits no relation from the four ordered inputs to those outputs.
Consequently, all 344 Poseidon2 output words are independent havoc values.
Even two opcodes with identical input vectors need not have equal outputs.

L0 asserts no Poseidon2 functionality, ground instance, collision, preimage,
injectivity, surjectivity, or permutation property.

### 2.2 L1: functional uninterpreted permutation

L1 changes only those 86 Poseidon2 opcodes. It applies one shared width-four
tuple function to every ordered four-input vector and equates the four opcode
outputs with the tuple result. Four scalar lane functions are an acceptable
SMT spelling only when they jointly represent that single construction.

Relative to L0, L1 adds exactly one fact: equal ordered inputs produce equal
four-word outputs. It adds no injectivity, no collision resistance, no
preimage resistance, no bijectivity, and no condition requiring distinct
inputs to have distinct outputs.

BN254 Poseidon remains exact field arithmetic in both plain L0 and plain L1.
The P1 region evidence below does not itself authorize replacing those regions
with uninterpreted functions. Any such replacement needs a separately checked
boundary-preserving abstraction.

## 3. P1 — checked BN254 Poseidon regions

than trusting debug metadata: every region is straight-line, every internal

The extraction records 77 logical constructions:

| construction | count |
|---|---:|

Seventy-five core regions contain 317 constraints, one contains 329, and one

larger for 35 regions because they include two materialization constraints;

### 7.2 Function identity

For Poseidon2, the locked `@zkpassport/poseidon2@0.6.2` width-four constants
and algorithm match the v5.0.0 Aztec/Barretenberg parameters: eight full
rounds, 56 partial rounds, exponent five, checked external/internal matrices,
and the D1P-15 H3 framing `[domain,left,right,3*2^64]` with lane-zero output.
All 86 program boundaries have that H3 construction.

For BN254 Poseidon, the Noir v0.3.0 optimized C/M/P/S tables for widths two,
three, and four equal the independent circomlibjs optimization output. The
locked `poseidon-lite@0.3.0` raw tables equal circomlibjs raw C/M tables, and
the installed `poseidon-solidity@0.0.5` `PoseidonT3.sol` is byte-identical to
the independently retrieved generator output from those tables. Framing is
`[0,input...]`, exponent five, output lane zero, with round schedules
8/56, 8/57, and 8/56 for arities one, two, and three. All 138 frozen H2 ground
terms also match execution of the actual Solidity library.

### 7.3 Canonical domains

All frozen ground inputs and outputs are canonical field values. Circuit
operands are field elements. The modeled burn rule must restrict every
precommitment and amount operand to `< P`.

The generated verifier result from D1P-12R remains separate: it rejected all
22 public-word `P`/`P+1` probes. The Solidity PoseidonT3 library behaves
differently at its library boundary: probes in either operand show that `P`
and `P+1` are reduced modulo `P`, not rejected. The model therefore cannot
silently treat arbitrary uint256 operands as distinct field elements. This is
a modeling obligation, not a vulnerability claim.

The P6 audit establishes construction identity and canonical-domain handling;
it does not establish collision resistance.
