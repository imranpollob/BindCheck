## 9. Proof-enforced hash/Merkle dependence

| Subject | Proof-enforced relation | Poseidon/Merkle/hash path |
| --- | --- | --- |
| amount | `amount >= max_fee`; amount is input to the commitment | `pre = Poseidon3(nullifier_preimage, secret, chain_id)`; `commitment = Poseidon2(pre, amount)`; commitment is an EVM/Aztec Merkle leaf |
| recipient | public field and `recipient_address != 0` | **none**: recipient is transcript/public-input bound, but not passed to a Poseidon or Merkle constraint |
| relayer/fee | `fee_factor != 1`, `priority_fee != 0`, `relayer_address != 0`, and `amount >= max_fee` | **none** for address, factor, priority, maximum or computed fee; `block.basefee` and the computed relayer fee exist only in the consumer |
| chain ID | public `chain_id` supplied by `block.chainid` | included in `Poseidon3(nullifier_preimage, secret, chain_id)`, then the amount commitment and Merkle membership |
| nullifier | public nullifier equals `Poseidon1(nullifier_preimage)` | direct Poseidon relation; it shares the private preimage with the chain-bound commitment but is not itself the Merkle leaf |
| EVM source root | commitment is a leaf in `origin_local_root` | 32-level Poseidon Merkle membership |
| Aztec source/domain | siloed hash uses configured `aztec_warptoad_address`; unique hash uses private nonce | two domain-separated Poseidon2 hashes, then 42-level Poseidon2 Merkle membership |
| giga/domain bridge | if origin and destination local roots differ, origin root belongs to `giga_root` | 5-level EVM-style Poseidon Merkle membership; deliberately bypassed in this same-root fixture |

The fee bound is therefore a joint relation, not solely a circuit hash
relation: the circuit proves `amount >= max_fee`; the consumer requires
`fee_factor × (block.basefee + priority_fee) <= max_fee` and mints the two
parts. The actual fee and block base fee are not proof inputs.

## 10. Required extension beyond exact occurrence matching

An eventual joint analyzer would have to model, without claiming they are
validated here:

1. the concrete Poseidon/Poseidon2 formulas, domain separators, Merkle index,
   path and depth relations, not merely calls named `hash` or `membership`;
2. strict field canonicality across Noir `Field` and Solidity
   `uint256`/`bytes32`/`address` representations;
3. the chain-domain path from consumer `block.chainid` through the commitment;
4. stored-root initialization/history, the same-root bypass, and cross-chain
   root-arrival conditions;
5. beneficiary policy for recipient selection and the consumer's special
   `address(1) → msg.sender` relayer substitution;
6. checked Solidity multiplication, addition and subtraction for the actual
   bounded fee split, including the unproved `block.basefee`;
7. the unused-to-used nullifier transition, rollback on later failure and
   repeated-call rejection; and
8. deployment correspondence among the fixed verifier address, generated VK,
   configured Aztec address and consumer bytecode.

Exact occurrence matching alone cannot establish those semantic, state and
environment relations. D1P-12R does not implement the joint analyzer and does
not validate the documented policy.
