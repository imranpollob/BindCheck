| input | FC-POS / FC-NEG | zero-fee |
|---|---:|---:|
| amount | `5000000000000000000` | `4000000000000000000` |
| fee factor | `974405002` | `0` |
| priority fee | `100000000` | `100000000` |
| max fee | `1000000000000000000` | `1000000000000000000` |
| FC-POS/zero next base fee | `100000000` | `100000000` |
| FC-NEG next base fee | `2000000000` | n/a |

Thus FC-POS has `max_fee < amount`, and the pinned consumer formula gives:

```text
FC-POS relayer fee
= 974405002 * (100000000 + 100000000)
= 194881000400000000 <= 1000000000000000000

FC-NEG relayer fee
= 974405002 * (2000000000 + 100000000)
= 2046250504200000000 > 1000000000000000000
```

There was no parameter search. `max_fee`, `priority_fee` and `fee_factor` are
all proof-bound public inputs. FC-NEG therefore changes only `block.basefee`;
altering a proof-bound value was never used as the negative control.

## 5. FC-NEG: unchanged valid proof, over-cap computed fee

The reverting transaction was deliberately submitted before FC-POS in the
fresh local execution. A reverted call leaves the nullifier available, so the
subsequent positive mint can remain in final local state without snapshots or
branch rollback. This chronological choice does not change the proof: the
generated verifier accepted it immediately before use, and FC-NEG/FC-POS
proof and calldata hashes are identical.

Transaction
`0x38fc8a51662ce311f28c4cb71c8a54feb5c4ba5b69142070d0ca1c43b7bf2185`
was mined with status `reverted`, gas used `4002199`, and an exact base fee of
`2000000000`. Its computed relayer fee is
`2046250504200000000`, exceeding the proof-bound `1e18` cap.

The transaction trace is marked `failed: true` and returns standard
`Error(string)` ABI data for `_relayerFee is larger than _maxFee`. This is the
require at pinned `backend/contracts/core/WarpToadCore.sol:166`, after public
input construction and verifier acceptance at lines 160–161. The trace has
395,121 opcode steps and is preserved in `fc-neg-receipt.json`; the report
does not treat trace size or timing as performance evidence.

All recorded consumer state is identical before and after the reverting
transaction:

- nullifier remains absent;
- relayer and recipient token balances remain zero;
- total supply remains `5e18`;
- backing-token balance remains `10e18`;
- cached local root and giga root remain unchanged.

A mined revert necessarily consumes the sender's transaction nonce and native
gas and advances the block. Those transaction-envelope effects are recorded
separately and are not described as unchanged state. The claim is precise:
the consumer's protected/token/root state changed by neither a partial
nullifier write nor a mint because EVM revert rolled the call back atomically.

## 10. Limitations and next step

This fixture concretely validates the pinned fee-cap and zero-fee behavior for
the chosen honest inputs and owned-local pre-state. It does not show that all
fee policies or all circuit/consumer bindings are correct, establish
cross-chain reachability, or replace the joint policy/analyzer work excluded
from this task. D1 remains **UNKNOWN**.

A separately authorized next task could specify and check the general
fee-policy relation across the proof/consumer boundary, with a measurable
completion criterion that all fee-bearing public-input occurrences and the
consumer base-fee dependency are represented in the joint model. That work
must not reinterpret this concrete fixture as a security verdict.
