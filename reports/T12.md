# T12 — Verifier-registry mapping and one zero-message settlement through the actual Payy consumer

Authorized defensive academic research: locally deployed contracts, owned test accounts, Foundry's local EVM. Revision `dcd5d96ee15664a59bc24ed0dc2bb78b73ac5e36`. **This is not advisory reproduction and not a BindCheck detection result.**
Reproduce: `bash scripts/t12.sh` (about a minute; reuses the T10 proof and public inputs, no proving). Evidence: `results/raw/T12/` (`observations/*.json` are compact execution observations).

## 1. The two hash values

| | Value @ `dcd5d96` | What it is | Evidence |
|---|---|---|---|
| Rust / deploy constant `AGG_FINAL_VERIFICATION_KEY_HASH` | `0x0701c58c…787c` | **Registry key.** Poseidon (Noir's BN254 `poseidon_hash`) over all fields of the circuit's `key_fields.json`, computed by Payy's own generator binary `pkg/zk-circuits/src/bin/vk_hash.rs` | **Mechanical:** running that binary on the committed `key_fields.json` reproduces `rollup.rs` (`pkg/contracts/src/rollup.rs`) and `eth/scripts/deploy.ts` exactly at both revisions (`0x122d2ac7…` at `c4d2c90`, `0x0701c58c…` at `dcd5d96`); `noir/agg_final/Nargo.toml` `hash_updates` tell the generator to write it into those two files |
| Generated Solidity `VK_HASH` | `0x0f8581a9…3328` | `bb`'s verification-key hash for the **keccak** oracle flavor, baked into the verifier for its Fiat–Shamir transcript (`agg_final.sol` l.8) | **Mechanical:** `bb write_vk --oracle_hash keccak` regenerates the committed key and gives this hash; the default-flavor hash is `0x267e6a2e…` and the flavors produce different key bytes |

**Intended to match? No: they are different identifiers by construction, and no code path compares them.** The consumer's lookup is `zkVerifiers[verificationKeyHash]` (`RollupV1.sol`, l.80, l.324–330, l.357): a `bytes32 → (verifier address, messages_length, enabled)` map keyed by whatever label the **prover supplies** in `verifyRollup`. Nothing relates that label to the verifier's embedded `VK_HASH`; what binds a proof to a circuit is the key baked into the registered verifier contract. Upstream's own deployment registers the Poseidon value (`deploy.ts` passes it to `initialize`, l.262–270), and the Rust client passes the same constant to `verifyRollup`. For the poseidon2-flavored `agg_agg` circuit the generator's Poseidon value and `bb`'s default hash coincide (T10 and this task); for the keccak-flavored `agg_final` they do not. What I established is that `bb`'s hash changes with the oracle flavor (`0x0f85…` keccak vs `0x267e…` default) while the generator's Poseidon value is fixed; I did not examine `bb`'s hash construction, so "`bb` applies the oracle's hash" is my reading, not a finding.

**Who registers/changes the mapping and how it is selected.** The contract `owner` (`OwnableUpgradeable`): `addZkVerifier(key, verifier, messages_length)` and `removeZkVerifier(key)` (`onlyOwner`), plus the one-time `initialize(…, verifierKeyHash, messagesCount, …)`. The owner also adds provers (`addProver`), validators (`setValidators`) and can `setRoot`. A registered **prover** (`onlyProver`) selects the verifier by passing the key as an argument. The proxy admin (the `ProxyAdmin` created by OZ's `TransparentUpgradeableProxy`) can additionally upgrade the logic; not exercised.

**Still unknown:** why the maintainers chose the Poseidon value as the registry identifier (not stated in the code I read), and whether they consider matching `VK_HASH` a requirement; I can only say the code never requires it. Neither constant was replaced.

## 2. Local deployment and assumptions

- **Consumer:** `eth/contracts/rollup3/RollupV1.sol` (SHA-256 `7062065c…`, unmodified) behind OpenZeppelin `TransparentUpgradeableProxy`, initialized as `deploy.ts` does: `initialize(owner, usdc, verifier, prover, validators, registryKey, 1000, noteKind)`. OpenZeppelin 5.0.1 comes from the npm tarballs; both match the integrity hashes in `eth/yarn.lock`. Compiled with solc 0.8.20, via-IR, optimizer 200 (the repo's `hardhat.config.ts`); Foundry compiled for `shanghai` (what solc 0.8.20 supports and what upstream produces).
- **Verifier:** deployed from Payy's committed `agg_final_HonkVerifier.bin` with `ZKTranscriptLib` deployed from its `.bin` and linked at the `linkrefs.json` offset, the same procedure as `deploy.ts` `linkAndDeployVerifier`. (T11 showed the Foundry-compiled verifier equals that `.bin` **after excluding the library-address slot and the trailing metadata**; T12 uses the committed `.bin` itself.)
- **Execution EVM must be Cancun or later.** I first ran on `shanghai`: the valid-proof settlement reverted with empty data after burning ~1.03 B gas (`40_shanghai_evm_failure.log`), while the controls behaved normally. The verifier bytecode contains an `MCOPY` (Cancun) opcode, so this is consistent with an invalid-opcode failure, but I did not trace the failing instruction. The tests therefore execute on `cancun` (upstream's Hardhat network uses `prague`).
- **Accounts and authorization:** `owner`, `prover` (added by `initialize`), `proxyAdminOwner`, and one validator whose key is derived from a fixed string, all local test identities. With one validator, `minValidators = (1·2)/3 + 1 = 1` signature. The signed digest is obtained from the consumer's own public `debugGetSignatureMessageHash(newRoot, height, otherHash)` and signed with `vm.sign`; `height = 1`, `otherHash` arbitrary. No signature check is bypassed.
- **Token:** a `LocalTestToken` stands in for `usdc`/the note kind (placeholders); 1,000,000 units are minted to the consumer so any unintended transfer would show.
- **Initial root (a fixture adaptation):** `initialize` hard-codes the empty-tree root `0x0577b5b4…79ff`, but the T10 fixture's `old_root` is `0x12e4daae…8898` (its synthetic tree already held notes). The owner therefore calls the normal administrative `setRoot(oldRoot)`. This is a stated assumption: the fixture does not come from a chain that started at the contract's initial root. Control 2 shows the unadjusted mismatch.
- `verifyCommitHash` is an empty placeholder in the source, so the commit hash is not checked by the consumer.

## 5. Limitations and next step

- One synthetic zero-message block; no mint/burn, no real token, one validator, no historical state. Acceptance here says the consumer, registry and verifier compose for this proof; it does not show anything about effectful messages.
- The compact observation schema (`bindcheck.consumer-observation/v0-compact`) is exploratory and has not been mapped onto BindCheck's record format; BindCheck was not adapted.
- **Blocker:** none for this milestone. **Smallest next step:** a separate task to generate a proof with one effectful message (a mint or burn) and settle it, which needs `mint()` registration, a real or faithful token and fresh proving; only then does consumer-side coverage of messages become observable.
