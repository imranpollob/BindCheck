# T04 — Research-authored coverage failure (controlled consumer mutation)

**Label:** research-authored mutant on self-authored contracts, local Foundry EVM, synthetic accounts, test ETH. Not a new real-world vulnerability. The T01 Groth16 setup is a toy with public, recomputable entropy, so nothing here speaks to adversarial soundness. No withdrawals, solvency claim or repair is part of this task.

## 3. The mutation (`results/raw/T04/mutation.diff`)
Beyond labeling/renaming (import path, doc header, contract name `ResearchMutantBackedBatchConsumer`), the only changes are:
- `submit(..., uint256 numRealTxs)`: extra parameter, **not** part of the ten verified public inputs; `numRealTxs > 4` reverts `InvalidNumRealTxs`.
- settlement loop `for (row = 0; row < ROWS; ...)` becomes `for (row = 0; row < numRealTxs; ...)`.
Old-commitment check, real verifier call (all ten inputs, T01 order), funding rules and per-row escrow checks are unchanged. Nothing requires rows outside the prefix to be neutral.

## 4. Experiment (same T01 proof: amounts [100,250,0,40], flags [1,1,0,1], 1000 → 1390)
Fresh deployments per test; fund only rows 0 and 1 (350 wei) unless noted. Measurement reads **raw storage slots** (`vm.load`; slot 0 commitment, slot 1 backing, slot 2 escrow mapping, cross-checked against getters in each test) and ETH balances, compared with T01 literals. No `vm.store`, `vm.mockCall`, forged proof, verifier bypass or circuit change.

| Scenario | Outcome | Measured |
|---|---|---|
| 1. Correct T03 consumer, rows 0,1 funded | reverts `MissingEscrow(3)` after verifier call | commitment unchanged (OLD); ETH 350; backing 0; all entries unconsumed; row 3 unfunded |
| 2. Mutant, `numRealTxs = 3`, rows 0,1 funded | **accepted** (no revert) | commitment OLD → NEW (`1308…0234`); entries 0,1 consumed; row 3 unfunded and unconsumed; ETH 350; backing 350 |
| 3. Control: mutant, rows 0,1,3 funded, `numRealTxs = 4` | accepted | commitment → NEW; entries 0,1,3 consumed; ETH 390; backing 390; missing 0 |

Independent calculation for scenario 2: required batch credit 390 (= 100+250+40 from the public amounts/flags); newly consumed matching backing 350 (raw storage); **missing required backing 40**; omitted obligation = this batch's **row 3** (active, amount 40; the only required-but-unbacked row). The initial 1,000 balance is outside this incremental-backing measurement.

**Violated invariant** (T03 §4): whenever the commitment advances, every active row of the batch must have had a funded entry of exactly its public amount consumed by that settlement. Here the commitment advanced with row 3's 40 units unconsumed and unbacked, deficit 40 of 390.

## 5. Evidence
- Proof/public inputs: all three calls log the same `keccak256(abi.encode(pA,pB,pC,pub))` = `0xfd847d58…c198e82` (3 logged, 1 distinct, `40_calldata_hashes.txt`); each test asserts the real verifier accepts the proof and `vm.expectCall` confirms the consumer called it with exactly those arguments.
- Witness and proof: rerun in this task, `snarkjs wtns check` → `WITNESS IS CORRECT` (`20_wtns_check.log`); `snarkjs groth16 verify` → `OK!` (`21_offchain_verify.log`); public order check OK (`22`).
- The violation test passes because it asserts the failure: its final assertion is `assertFalse(invariantHolds, "intended research mutation must make the invariant fail")`.
- **Causal check (throwaway edit, restored, hash verified):** changing the loop bound back to `ROWS` makes exactly that test fail with `MissingEscrow(3)` (`50_causal_check_bound_neutralized.log`), so the bound is the cause.
- Mutant keeps other checks (`test_mutant_retainsOldCommitmentProofAndBoundChecks`): `numRealTxs=5`, altered amount, stale old commitment, wrong/duplicate/inactive funding, and `MissingEscrow(3)` at `numRealTxs=4` all revert with state unchanged.

## 7. Assumptions, limitations, observations
- Attacker assumption exercised: any caller can invoke the mutant's `submit` with the honest, normally generated proof and choose `numRealTxs`; no storage tampering or privileged role. The consumer contains the self-authored flaw by construction.
- `numRealTxs` is unauthenticated: the circuit cannot constrain it, which is the point of the case. A repair would process all active rows or require rows outside the prefix to be neutral; not attempted here.
- The "required" set is derived from this demonstration's batch identity `(batchId,row)` with 1 unit = 1 wei; it is not a general deposit model. Public inputs and funding amounts are on-chain; commitments are unsalted (no confidentiality).
- Open from T02/T03, not investigated: the ~1.07B-gas off-curve proof-point case (still visible in the T02 test).
- Not run: fresh-machine rehearsal, other `numRealTxs` values with partial funding (0, 1, 2), withdrawals/solvency, repair.

## 8. Recommended next (T05)
Repair the mutant (process every active row, or enforce neutrality outside the prefix), then show the failing case blocked while honest, padded/empty and fully funded batches still settle. Completion: scenario 2 rejected by the repair, scenarios 3 and padding accepted.
