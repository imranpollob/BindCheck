# T21 — Source-based check for message-tail derivation

Authorized defensive academic research; desk analysis of circuit source only. **No proofs generated, no transactions, no upstream file modified** (sources are read from git objects of `tools/cases/payy-history`; its status is unchanged from T15). Revisions: **A** `c4d2c9021b8fb9988816eb6987a734b830bfce15` (earlier), **B** `dcd5d96ee15664a59bc24ed0dc2bb78b73ac5e36` (check added). `agg_utxo` is byte-identical at A and B.
Reproduce: `bash scripts/t21.sh` (under a second). Prototype: [scripts/t21_tailcheck.py](../scripts/t21_tailcheck.py) (stdlib Python, 573 non-blank lines), mutants [scripts/t21_mutants.py](../scripts/t21_mutants.py). Evidence: `results/raw/T21/` (`00_preregistration.md`, `01_manual_review.md`, `10_source_hashes.txt`, `20_cases.txt`, `30_mutants.txt`, `50_artifact_sidecheck.txt`, `src/`).

**Read this first — what this result is not.** The Payy tail bug is the already-public advisory (GHSA-fhxc-63vg-9gwr / CVE-2026-48100, see T20); nothing here is a new finding. I had read the three sources and reports T15–T20 *before* writing the pre-registration and the analyzer, so the analyzer's patterns are fitted to these exact files and the manual review is not blind. The three verdicts are therefore **in-sample agreement, not evidence of generalization.**

## 1. Pre-registered (before the analyzer existed; `00_preregistration.md`, sha256 `41141da6…5303`)

- **Property.** In `main`, let M be a public message array and c a counter (mutable local, init 0, only `+= const`). Every word of M the circuit reads must lie below final c and be bound to a value of a proof checked by `verify_proof(_with_type)`; every index ≥ final c must be constrained to 0 by an assertion that always executes.
- **Evidence needed** (source only): E1 parse; E2 identity of M and c; E3 all writes to c; E4 every use of M accounted for; E5 each read M[c+k] covered by later increments in its block; E6 dataflow from a read to the public-inputs argument of `verify_proof_with_type`; E7 for a tail check: full-length loop, guard exactly `i >= c`, `assert(M[i]==0)`, top-level in `main` after the last write to c.
- **Verdicts.** SATISFIED = E1–E7 and a tail check exists. UNCONSTRAINED = E1–E6 hold, every use of M is a counter read, no tail check, so no constraint reads any index ≥ final c. Otherwise UNKNOWN.
- **Must be UNKNOWN:** parse failure; no unique message array; counter written in any way other than `+= const`; M used in an unexplained way (alias, hashed whole, computed index); read coverage not provable or unresolved callee; tail check of any non-recognised shape or placement; no connection to a verify sink; `unsafe`/`unconstrained`/oracle present.

## 2. What the prototype does

A ~200-line Noir-subset lexer/parser (functions, structs, `let`, `for`, `if`, `assert`, calls, indexing; **anything unparsed → UNKNOWN**, which happened during development: an `assert(cond,)` form made agg_agg return UNKNOWN until I added it). Then, on the AST of `main` (and of any function that receives M, with parameter binding):
1. find M (the only `pub` array read at a counter-based index) and c; check all writes to c;
2. classify every occurrence of M; compute read coverage; look for the tail-check shape and its placement;
3. build a flow- and scope-insensitive variable graph and look for a path from an M-read to the value passed as the public-inputs argument of `verify_proof_with_type`; trace path variables back to `main` parameters.

## 4. Project-specific assumptions and manual work

- **Annotations required: 0** (M and c are auto-detected). One optional flag (`--message-array`) gives the same verdicts.
- **Patterns that are hard-coded and would need rewriting for other circuits** (all chosen after seeing these files): (P1) counter = `let mut c = 0` changed only by `+= const`; (P2) M read as `M[c]` or `M[c + const]`; (P3) tail check shape exactly `for i in 0..len(M) { if i >= c { assert(M[i] == 0) } }`, inline or in a one-hop callee with M and c passed by name; (P4) sink = `std::verify_proof[_with_type]`, arg index 2; (P5) the check must be a top-level statement of `main` after all counter writes; (P6) Noir features accepted by the parser (no generics, struct literals, `as`, closures, imports across packages).
- **Cost.** Writing the parser and analysis plus three debugging rounds (trailing-comma assert; loop variable mistaken for a counter; provenance sink wrongly including an `if` condition) took far more effort than the manual review, which was 477 lines across three files and about a 30-line diff. The tool runs in <1 s. For three cases it is more expensive than reading; it only pays off if re-run on many similar circuits, which this task did not test.

## 5. Comparison with the manual review (`01_manual_review.md`, written before any run)

Verdicts agree on all three (A: tail unconstrained; B and agg_utxo: constrained to zero). Both identified the same counter, prefix reads, tail check and its position. What the manual review noted that the tool does not capture: padding proofs get a substituted public-input array (l.85–96) and are all-zero by `has_ended`, so they contribute no prefix words; the compaction rules (kind 2 = 4 words, kinds 3/4 = 5 words, no gaps); that every slot below c is actually read. What the tool did that I would not do by hand: the explicit coverage check for index ≥ final c and the mechanical rejection of look-alike variants (mutants). Since the review was not blind and the tool was fitted to the same files, agreement shows consistency, nothing more.

## 6. Limits and what is missing

- **UNCONSTRAINED means only what the source says:** no constraint reads those slots. Whether a real prover can exploit it is the T15–T18 result, not this tool's.
- Provenance is variable connectivity, flow- and scope-insensitive; it does not prove that, when a word is active, the array passed to the verifier is the one it was matched against (the padding-proof substitution in agg_agg is not reasoned about). The prefix is not proven to be fully read below c.
- Branch feasibility, arithmetic wraparound (e.g. c exceeding 1000) and field-vs-integer semantics are not modeled; ACIR/SSA is not used, so source-to-constraint fidelity rests on the T15 compile equality.
- Not shown: any behaviour on circuits other than these three (plus `agg_final`'s UNKNOWN), on other Noir versions, or on held-out aggregation circuits with unknown status. Nothing here shows the analyzer would have found the bug before the advisory.
- To make the result general one would need an independent corpus of aggregation circuits with labels written by someone who has not seen the analyzer, and either an ACIR-level formulation or a broader parser.
