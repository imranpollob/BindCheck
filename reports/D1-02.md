## WarpToad

The pinned [Noir producer](https://github.com/warptoad/warp-toad/blob/973e7d1e4b60d0d8a8ca299b0cabd9193b147ef8/backend/circuits/withdraw/src/main.nr)
declares eleven public Field parameters. The
[consumer](https://github.com/warptoad/warp-toad/blob/973e7d1e4b60d0d8a8ca299b0cabd9193b147ef8/backend/contracts/core/WarpToadCore.sol)
constructs eleven verifier words in this source order:

| Index | Producer role / consumer source expression |
| ---: | --- |
| 0 | nullifier |
| 1 | chain ID / `block.chainid` |
| 2 | amount |
| 3 | giga root |
| 4 | destination local root |
| 5 | Aztec WarpToad address / configured contract value |
| 6–8 | fee factor, priority fee, maximum fee |
| 9–10 | relayer and recipient, encoded from EVM addresses |

This is a manually inspected source mapping, not recovered compiled ABI or a
proved representation relation. `mint` checks admitted roots and nullifier
use, calls `IVerifier.verify`, and mints balances with an optional relayer fee.
Its source path handles one claim, not the required batched transition.

The [same-chain test](https://github.com/warptoad/warp-toad/blob/973e7d1e4b60d0d8a8ca299b0cabd9193b147ef8/backend/test/testL1ToL1.ts)
contains local funding/wrap, burn, proof generation, verifier call, mint and
balance assertions. The inspected proving helper calls Noir execution and
UltraHonk proof generation/verification with `keccakZK: true`; the verifier
generation script uses the same named mode. These are source-supported routes,
not observed successful executions. The root README still expects an Aztec
sandbox/local node; `setupEvmOnlyEnvironment` omits Aztec contract deployment
but does not itself establish a self-contained local chain.

Concrete unresolved prerequisites:

- The README names nargo/noir_js beta.19, while the backend package pins
  noir_js beta.22 and bb.js 5.0.0; the root compile script invokes
  `aztec-nargo`. The README also mentions an older nightly bb.js. No version
  combination was chosen by guesswork or tested.
- The compiled frontend circuit is present in the pinned tree but is above
  the 1.5 MB per-file screening bound and was not fetched. No compiler output,
  verification-key, generated verifier, and consumer correspondence was proved.
- Root initialization, standard-token assumptions, fee policy, field/address
  canonicality, and cryptographic/Merkle semantics remain to be modeled.
- The source has a public test mint/faucet path. Any later policy would need
  to identify precisely which effects it protects and admits; no global
  supply/backing guarantee is inferred from the proof-consuming path.

Exposure: the source contains an explicit defect-warning annotation, read
incidentally during the mapping. It was not investigated, reproduced, or
promoted into a finding. The annotated mechanism cannot be presented as a
blind holdout. No audit/issue hunt or mutation was performed.

## 0xbow Privacy Pools

The [Circom producer](https://github.com/0xbow-io/privacy-pools-core/blob/d494b63e79f33bb2b0c8ece6cdacdca465c3b884/packages/circuits/circuits/withdraw.circom)
is instantiated as `Withdraw(32)` by the pinned build script, which explicitly
lists six public inputs. Two outputs precede them in the eight-signal mapping
documented and accessed by
[ProofLib](https://github.com/0xbow-io/privacy-pools-core/blob/d494b63e79f33bb2b0c8ece6cdacdca465c3b884/packages/contracts/src/contracts/lib/ProofLib.sol):

| Index | Source role |
| ---: | --- |
| 0–1 | new commitment hash, existing nullifier hash |
| 2 | withdrawn value |
| 3–4 | state root and tree depth |
| 5–6 | ASP root and tree depth |
| 7 | withdrawal context |

Compiled signal order and key correspondence remain unvalidated. The
[pool](https://github.com/0xbow-io/privacy-pools-core/blob/d494b63e79f33bb2b0c8ece6cdacdca465c3b884/packages/contracts/src/contracts/PrivacyPool.sol)
checks caller/context/root conditions, invokes the Groth16 verifier, marks a
nullifier spent, inserts the new commitment and transfers funds to the
processor. The ERC20 implementation uses SafeERC20 transfers.

The [batch consumer](https://github.com/0xbow-io/privacy-pools-core/blob/d494b63e79f33bb2b0c8ece6cdacdca465c3b884/packages/contracts/src/contracts/BatchRelayer.sol)
decodes batch data, requires a nonempty batch with the declared size, calls
the pool once per proof, checks the accumulated total, then distributes the
net amount and fee. This is batched consumption of individual proofs, not a
Payy-style recursive aggregate. Source comments state incomplete-batch
prevention intent. This is a useful prospective policy source, not an
assumption that the implementation already satisfies it.

The pinned protocol withdrawal documentation and circuit README describe
ownership/membership, amounts, context and relaying. The protocol document's
example `Withdrawal` struct has a `scope` member; the actual interface has
only `processooor` and `data`, with pool `SCOPE` encoded separately in the
context check. Future specifications must separate policy intent from actual
encoding instead of copying that example as an implementation fact. No
policy was frozen or independently human-reviewed in this task.

The SDK uses `snarkjs.groth16.fullProve`. The integration helper invokes a Node
proof generator through Foundry FFI and ABI-decodes its result. The integration
base deploys a concrete WithdrawalVerifier; success tests cover one/two-proof
batch flows. The SDK artifact loader performs integrity checks, but the
source-to-distributed-artifact-to-verifier chain was not validated here.
The Git tree inventories WASM, R1CS, zkey and vkey artifacts; only the small
vkey was fetched. No large proving artifacts or setup were executed/downloaded.

Concrete unresolved prerequisites:

- Circom 2.2.0/Groth16 is outside the initial Noir/ACIR frontend. A new
  producer adapter is an evaluation question, not an existing capability.
- Pooling amounts and splitting recipient/fee payments exceed the initial
  occurrence-only implementation fragment until their policy semantics and
  controls are implemented. No aggregate result is claimed.
- The existing integration setup calls `createSelectFork` with a mainnet
  RPC and uses CreateX and an ERC1967 proxy. A fork-free initialization with
  owned synthetic assets and a supported consumer path would require separate
  work. No RPC request, proxy analysis or upstream test was executed here.
- Hash/context encoding, key consistency, ASP/root history and standard-token
  assumptions still need explicit justified models.

Exposure is source/schema/test-intent inspection, including success-test names;
audit reports and defect-label suites were not read. The family becomes development data if later tuning uses its results. It is not yet a
held-out evaluation result.
