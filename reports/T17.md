# T17 — Source analysis: how would the T16 message be interpreted, and under what conditions would it execute?

Authorized defensive academic research; source reading only, at the exact earlier Payy revision used by T15–T16: `c4d2c9021b8fb9988816eb6987a734b830bfce15`. **No contract is deployed and no transaction is run in this task.** All line references are to `eth/contracts/rollup3/RollupV1.sol` and `noir/utxo/src/main.nr` at that revision (byte-identical to the later revision per T15's diff-stat). Reused: T15/T16 artifacts, no new proof.

**Research question.** Could a burn-shaped message that was never derived from an inner transaction cause a committed token transfer through the consumer? Which checks or authorization assumptions could prevent that?

**Short answer.** Mechanically, yes — if such a message is a decoded message in an accepted `verifyRollup` call, `verifyBurn`/`executeBurn` will attempt an ERC20 transfer with no check that the message came from any inner proof, because **burn has no registration analogous to mint's `mints[hash]`.** But reaching "accepted" requires: (1) the caller to be a whitelisted prover, (2) a quorum of the *current* validator set to have signed, and (3) — at the earlier revision only — the unconstrained circuit tail (T15/T16). At the revision actually carrying the fix, step 3 is closed inside the circuit itself, before any contract code runs. Whether (1)/(2) could be subverted, and whether the deployed system ever ran the unfixed circuit, are not addressed by this source reading.

## 1. Call path, traced from source

`verifyRollup` (l.314, `onlyProver`) → in order: verifier-registry lookup and `publicInputs.length == messages_length + 3` (l.323–332) → `verifyRootHash(oldRoot)` (l.338, `== rootHash`) → `verifyCommitHash(commitHash)` (l.340 — **a no-op placeholder**, l.382: `function verifyCommitHash(bytes32 commitHash) internal {}`) → `verifyValidatorSignatures(newRoot, height, otherHashFromBlockHash, signatures)` (l.342) → `verifyAllMessages(3, publicInputs, messages_length)` (l.349) → `zkVerifiers[...].verifier.verify(aggrProof, publicInputs)` (l.357) → state update and `RollupVerified` (l.364–371). This order is read from source, not executed; T12–T14 already executed this same order for mint messages.

`verifyAllMessages` (l.384) walks `publicInputs` from index 3 to `3 + messages_length`, calling `verifyMessages` (l.397) repeatedly; each call reads `kind = publicInputs[index]` and dispatches: `0` → `index+1` (padding, no-op), `2` → `verifyMint` (`+4`), `3` → `verifyBurn` (`+5`), anything else → `revert("RollupV1: Invalid message kind")`. **The walker's position is entirely determined by the sequence of kind tags and fixed arities seen so far** — there is no separate length field per record. A burn record is only parsed as such if the walker lands exactly on its `kind=3` word; T16's record was placed at `messages_index`, the position the walker reaches immediately after the preceding mint record's own `+4` advance, so by source reading it is parsed as a fresh record, not absorbed into the mint record or skipped as padding (not executed in this task).

`verifyBurn` (l.442): `note_kind = messages[i+1]`, `value = uint256(messages[i+2])`, `hash = messages[i+3]`, `burn_addr = bytes32ToAddress(messages[i+4])`; looks up `token = tokens[note_kind]`; computes `substituteBurnKey = getSubstituteBurnKey(hash, burn_addr, note_kind, value)` (l.486, `keccak256(abi.encode(hash, burnAddress, noteKind, amount, uint256(0)))`); if `substitutedBurns[key] != 0`, pays that substitutor instead of `burn_addr` and clears the entry; else pays `burn_addr` directly. Either way it calls `executeBurn` → `executeBurnToAddress` (l.516): a raw `token.call(abi.encodeCall(IERC20.transfer, (recipient, value)))`, success defined as "`.call` itself didn't fail" **and** ("no return data" **or** "return data decodes to `true`"). **No `require` follows** — `verifyBurn`/`verifyAllMessages`/`verifyRollup` do not check `executeBurn`'s return value; a failed transfer does not revert the block.

**`substitutedBurns` (l.551–604, `substituteBurnTo`):** an *optional*, privileged (`onlyBurnSubstitutor`, owner-granted) side channel: a substitutor can pre-pay `burnAddress` immediately, pulling `amount` from themselves via `safeTransferFrom` and recording `substitutedBurns[key] = substituteAddress`; when the matching burn message is later rolled up, `verifyBurn` reimburses the substitutor instead of the original address. This path requires its own separate authorization (`onlyBurnSubstitutor`) and funds (the substitutor's own balance); it is not a path by which an unbacked message alone moves funds — it only changes *who* is reimbursed for a burn that already executes.

## 2. Decoded T16 record (outer public-input indices 7–11; message array indices 4–8)

| Outer idx | Field | Value (from T16) | Meaning | Encoding / range | Unit |
|---|---|---|---|---|---|
| 7 | kind | `3` | selects the burn branch in `verifyMessages` | raw `uint256(bytes32)`; only `0,2,3` are legal, else revert | — |
| 8 | note_kind | `0x0002…893c…3359…` | asset-type tag; `tokens[note_kind]` resolves it to an ERC20 address | opaque 32-byte constant, defined off-chain/in the Rust fixtures (here, the same `bridged_polygon_usdc_note_kind()` used by the active mint) | — |
| 9 | value | `7` | amount `executeBurnToAddress` will try to `transfer` | raw `uint256`; for a **genuine** burn proof, the contributing utxo circuit bounds it to 240 bits (`msg_value.assert_max_bit_size::<240>()`, `noir/utxo/src/main.nr` l.54); **this synthetic word was never range-checked by any circuit**, only by this contract reading it as a `uint256` | smallest unit of the mapped ERC20 (no decimal/USD conversion here) |
| 10 | hash | `0x…67932` (424242 decimal) | for a genuine burn, must equal `commitments[0]`, the Merkle commitment of the spent input note (`noir/utxo/src/main.nr` l.71, comment at l.68); used **only** as part of the `substitutedBurns` lookup key — `verifyBurn`'s direct-payout path does not check it against anything | arbitrary field element; comment at l.59–64 of the circuit: "any hash can be used \[for a real burn\] ... this is acceptable" | — |
| 11 | burn_addr | `0x…dead` | recipient of the transfer (direct path) | `bytes32ToAddress` (l.472) takes the **low 160 bits only**; nonzero upper 96 bits are silently dropped, not rejected. For a genuine burn, the circuit binds this to a *private* witness `pmessage4` (l.90: "Prevent frontrunning the txn and changing the evm address") so the address cannot be swapped after proving; this synthetic word has no such binding because it never passed through that circuit | Ethereum address |

**Does the preceding sequence or padding change the interpretation?** Yes, by construction of the walker described above: the record is parsed as a burn only because the walker's position after the mint record's fixed `+4` advance lands exactly on this word. Any different preceding sequence (a different kind, a different count of preceding records, or this word sitting inside what should be a trailing-zero region) would change which word the walker treats as a `kind` tag, up to and including a revert (`"RollupV1: Invalid message kind"`) if the walker lands on a value that is not `0`, `2`, or `3`. This is a structural reading of `verifyAllMessages`/`verifyMessages`, confirmed only by inspection — not executed.

## 3. Execution prerequisites and what would block the path

| Prerequisite | Mechanism | Who holds it |
|---|---|---|
| Caller permission | `onlyProver` (l.152): `provers[msg.sender] == 1`, set only by `onlyOwner` via `addProver` | an explicitly whitelisted address, **not** an ordinary user |
| Validator signatures | `verifyValidatorSignatures` (l.725): ECDSA-recovers each signer, requires `signatures.length >= 2/3·|validatorSet| + 1`, each signer in the *current* validator set, signers strictly sorted (no duplicate) | a quorum of whitelisted validators; set via `_setValidators`/an owner-controlled mechanism (not traced further here) |
| What the signature actually covers | `getSignatureMessageHash(newRoot, height, otherHashFromBlockHash)` (l.767) — **a function only of these three values**, not of `aggrProof`, not of `publicInputs`/the message array, not of `verificationKeyHash` | — |
| Commit-hash check | `verifyCommitHash` — **a no-op** in this source | none enforced on-chain |
| Stored root | `verifyRootHash`: `oldRoot == rootHash` (current contract state) | advances only through a prior accepted `verifyRollup` |
| Verifier registry | `addZkVerifier` (`onlyOwner`): binds a `verificationKeyHash` to a deployed verifier contract and a `messages_length`; `verifyRollup` requires `zkVerifiers[...].enabled` and the exact `publicInputs.length` | owner-controlled; must match the circuit the proof was built for |
| Token mapping | `tokens[note_kind]`, set by `initialize`/`addToken` (`onlyOwner`) | owner-controlled |
| Available balance | **none enforced for burns** — `executeBurnToAddress` simply attempts `token.transfer(recipient, value)` from whatever balance the consumer currently holds | the consumer's own ERC20 balance at call time |
| Burn-specific registration / single-use check | **none** — contrast with mint's `mints[hash]` (`amount`, `note_kind`, `spent`, checked and flipped in `verifyMint`, l.418–440); `verifyBurn` reads `hash` only to look up an *optional* substitutor | — |
| Circuit-side constraint on the message (the only mechanism that *would* tie the message to a real transaction) | at the earlier revision, none, for a word beyond `messages_index` (T15); at the revision with `assert_message_tail_zero`, such a word is rejected inside `agg_agg`'s own witness generation, before any contract call (T15, confirmed; not re-run here) | the circuit, not this contract |

**Mechanically checked (T15/T16, reused, not rerun here):** at the earlier revision, a burn-shaped word placed past the real messages is witness-satisfiable in `agg_agg`, the resulting proof natively verifies, and it propagates through `agg_final` unaltered, landing at outer indices 7–11 as decoded above.
**Source-confirmed (this task):** the call order above; that burn has no registration or single-use check; that the validator signature covers only `(newRoot, height, otherHash)`; that `verifyCommitHash` is a no-op; that a failed `executeBurn` does not revert the surrounding call; that `bytes32ToAddress` truncates rather than rejects; that the earlier revision's own committed Solidity verifier bytecode exists locally (`eth/contracts/noir/agg_final_HonkVerifier.bin` + `.linkrefs.json` + `agg_final_ZKTranscriptLib.bin`, matching the format T12–T14 already deployed for the later revision), so a matching local deployment is not blocked on missing artifacts.
**Unresolved / explicitly not established:** whether off-chain validators reconstruct and check the full message list against the inner proofs before co-signing (nothing in this contract does so; if they do, that external diligence — not this contract — is what would stop an unbacked message, and this task has no visibility into it); how the prover and validator keys are actually provisioned and secured in a live deployment; whether the earlier, unfixed circuit revision was ever deployed on any live network, and if so for how long before the fix; whether an EVM call to an address with no code (e.g. an unset/misconfigured `tokens[note_kind]`) would report `success = true` with no tokens actually moved — a general EVM semantics point consistent with the source above, but not executed or confirmed in this testbed.

## 4. Transfer semantics

- **Recipient selection:** `burn_addr` directly, unless a matching `substitutedBurns` entry exists, in which case the registered substitutor is paid instead and the entry is cleared.
- **Amount:** exactly `value` as decoded from the message; no scaling, no fee, no partial-fill logic.
- **Token-return handling:** `executeBurnToAddress` treats a `.call` that reverts, or that returns `false` from a compliant ERC20, as failure; a token with no return value (the common non-standard pattern) is treated as success as long as the call itself did not revert.
- **Reverts:** a failed transfer does **not** revert `verifyBurn`, `verifyAllMessages`, or `verifyRollup` — the block is still accepted, the root still advances, and the only visible effect is `success = false` in the emitted event.
- **Does a reported `Burned` event imply a successful transfer?** **No.** The event is emitted on both outcomes and carries an explicit `success` boolean (l.57–61, l.511–513); a reader must check that field, not merely the event's presence.

## 5. Candidate security property (implementation-independent)

**Property.** In any block a consumer accepts (`verifyRollup` returns without reverting), every message it interprets as a burn should correspond to a burn-kind transaction that was itself authorized and balanced by the private circuit: owned input notes of sufficient value, consumed exactly once, with the hash and recipient address bound into that same proof. Equivalently: no accepted burn's four fields should be satisfiable by a message that cannot be traced to a real, constrained burn-kind proof contributing to that same aggregate.

**What would establish a violation.** Observing, through the actual deployed verifier and consumer (not a native-only or earlier-revision check), an accepted `verifyRollup` call whose decoded burn record cannot be traced to any inner burn-kind proof folded into that aggregate, **together with** `executeBurn` reporting `success = true` and an observable balance change consistent with a real transfer out of the consumer. Both halves are needed: proof-level acceptance alone (T16) is not a violation of this property by itself, since the property is about what reaches the consumer and executes with effect, not what a circuit alone permits.

**Outcomes that would instead show rejection, harmlessness, or a missing assumption, not a violation:**
- The recursive proof is rejected by the deployed verifier (this is what happens at the fixed revision, per T15 — not a violation, a prevention).
- The message is accepted by the circuits but parses, under `verifyAllMessages`'s walker, into an unintended position (absorbed into a different record, read as padding, or triggers `"Invalid message kind"`) — no burn is executed.
- `executeBurn` is attempted but returns `success = false` (insufficient balance, or a token that reverts) — no tokens move, regardless of circuit acceptance.
- The block is never submitted at all because an authorized prover and a validator quorum never cooperate — a missing-prerequisite case, not a property violation, and the one this source reading cannot resolve (off-chain validator diligence is outside this contract).

## 6. Minimal local test recommendation (not run in this task)

**Comparison:** the existing T16 **candidate** `agg_final` proof/public inputs versus its **control** counterpart, submitted to two separately deployed, otherwise-identical local instances of the *earlier revision's own* consumer and verifier (its own committed `agg_final_HonkVerifier.bin`/`ZKTranscriptLib.bin`/`linkrefs.json`, confirmed present at this revision in §3 — not the later revision's), using our own owned prover and validator keys exactly as T12–T14 already did (normal, authorized local testing, not a simulated external attacker).

**Must match between the two calls:**
- the same fresh deployment pattern (each case on its own freshly initialized consumer, since `old_root` is identical between control and candidate — both are the empty-tree root — so either one, submitted first, would consume that root on a shared instance);
- the same `initialNoteKind`/`tokens[note_kind]` mapping (already the note kind both T15 messages use);
- the same pre-funding step: a normal `mint()` registration and settlement (T13's pattern) before the burn test, so the consumer holds a real, observable balance (e.g. 100 units) before either call — otherwise a "successful" burn and a balance-insufficient failure cannot be told apart;
- the same owned validator key(s) signing `(newRoot, height, otherHashFromBlockHash)`.

**What must differ:** only the `aggrProof`/`publicInputs` bytes submitted (control's vs. candidate's, from T16), and — a fact worth testing explicitly — **nothing else needs to differ in the validator signature**, because `newRoot`, `height`, and (if used) `otherHashFromBlockHash` are identical between the control and candidate proofs (T16, §2); on source reading, the same signature set would satisfy `verifyValidatorSignatures` for either submission.

**Can the current candidate execute as-is?** Yes, mechanically, without a new proof: T16's candidate is a complete, independently-verifying `agg_final` proof with the exact `publicInputs` length (`1003 = 1000 + 3`) a registered earlier-revision verifier expects, and its `old_root`/`new_root` already match what a freshly initialized consumer would hold. **A new proof would only be needed** to vary a field already baked into this one — e.g., a different `value`, `burn_addr`, or `note_kind` than `7` / `0x…dead` / the bridged-USDC tag already fixed in the existing candidate — since T15/T16's own tamper controls already showed that altering any public-input byte without a matching new proof fails verification.

## Summary

- **Decoded record** (outer indices 7–11): kind=3 (burn), note_kind = bridged-USDC tag, value=7 raw units, hash=424242 (an arbitrary field, not checked against anything in the direct-payout path), burn_addr=`0x…dead` (low 160 bits only). Interpretation depends on the exact preceding sequence of kind tags and arities (source reading, not executed).
- **Execution prerequisites and blocking checks:** authorized prover + a validator-set quorum signing `(newRoot, height, otherHash)` only (not the proof or messages) + a registered verifier/token mapping + sufficient existing consumer balance; **burn has no registration or single-use check** (unlike mint); at the fixed revision the circuit itself blocks an unbacked tail word before any of this runs.
- **Candidate property:** every accepted burn should trace to a real, circuit-authorized burn transaction; a violation needs both an untraceable accepted message **and** an observed successful transfer, not proof acceptance alone.
- **Minimal local test:** T16's candidate vs. control `agg_final` proofs, submitted to two fresh, pre-funded, earlier-revision consumer deployments under owned prover/validator keys; executable with the existing proof, no new proving needed unless a different field value is wanted.
- **Unresolved:** off-chain validator diligence, prover/validator key provisioning in any live deployment, whether the earlier circuit was ever actually deployed live, and the zero-code-token-address EVM nuance (reasoned, not executed here).
