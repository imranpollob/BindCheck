# T14 — The Payy mint proof-to-consumer obligation: specification and direct test

Authorized defensive academic research; local contracts, owned test accounts, Foundry's local EVM. Revision `dcd5d96ee15664a59bc24ed0dc2bb78b73ac5e36`, pinned toolchain, T13 mint proof and T10 zero-message proof reused (no proving).
**Not a vulnerability claim, not advisory reproduction, no BindCheck functionality.** Reproduce: `bash scripts/t14.sh`. Evidence: `results/raw/T14/` (`10_obligation_trace.txt`, `hash_check.json`, `observations/*.json`, `51_forge_results.txt`, `90_summary.json`).

## 1. The property being tested

**In plain language.** For one call of `RollupV1.verifyRollup` with public inputs `[old_root, new_root, commit_hash, messages…]`:
1. If the call is **rejected**, nothing protected changed (root, height, each watched mint entry, every token balance).
2. If it is **accepted**: the stored root was `old_root` and becomes `new_root`, and the height rose to the submitted height; **every** decoded mint record (identity `h`, note kind `k`, value `v`) matched a registration `mints[h] = (k, v, unspent)` that existed before the call and is **spent afterwards** with kind and amount unchanged (one-time consumption); the consumer's token balance covers the consumed values (the escrow is held, nothing is released at settlement); no mint entry not named in the messages changed; no identity is consumed twice by one call.
3. With **no** mint record, 2's mint clauses are vacuous: no watched mint entry may change.

**As a direct assertion.** `MintProperty.property(accepted, pre, post, publicInputs, height, watched)` in `payy-consumer/test/MintObligation.t.sol` (plain Solidity, returns a verdict and reason; it re-implements the message grammar from the sources below and calls neither the consumer's decoder nor any BindCheck code). It is applied to every case, and exercised on **nine hand-built violating snapshots** (`test_propertySelfCheck_handBuiltSnapshots`: not consumed, wrong-value registration, no registration, already spent, escrow released, unrelated entry changed, wrong root, rejected-but-changed, zero-message block that consumes a mint), so it can say "no"; those are not executions.

## 2. Source evidence

Citations are to the pinned revision; excerpts with line numbers are in `10_obligation_trace.txt`.

**Mechanically checked**
- The T13 proof verifies natively and in the real Solidity verifier; its decoded mint is kind 2, note kind `0x0002…893c499c…3359`, value 100, hash `0x1e05013a…d103` (T13).
- **The mint hash is the hash of the two output notes' `psi` values, not of the commitments.** `t14_hash_check` (Rust, no proving): `hash_merge([psi0, psi1])` = `Utxo::mint_hash()` = the hash in the verified public inputs (`0x1e05013a…`); `hash_merge([commitment0, commitment1])` = `0x1d23937f…`, which differs.
- The five cases and one reference case below, and the assertion's self-check, ran as recorded.

**Source-confirmed**
- *What the proof establishes* (`noir/utxo/src/main.nr`, mint branch l.76–87; `noir/agg_utxo`, `noir/agg_agg`): the message is `[2, note_kind, value, hash]`, `value ≤ 2^240`, `output_value == input_value + value`, `hash == Poseidon2(output_notes[0].psi, output_notes[1].psi)` (l.66), `output_notes[0].kind == note_kind`; `agg_utxo` places the four words at the front (`messages_index += 4`) and `agg_agg` compacts kind 2 as four words. The Rust builder agrees (`pkg/zk-primitives/src/utxo.rs` `messages()` and `mint_hash()` l.104–131).
- *The comment does not match the code.* `RollupV1.sol` l.90 says "mints are removed after the rollup validates them. Mint hash is hash of commitments." The implementation hashes `psi` values (above) and `verifyMint` sets `spent = true` and keeps the entry; nothing deletes it.
- *Registration* (`RollupV1.mint`, l.619–646): callable by **anyone**; refuses a hash whose recorded `amount != 0` ("Mint already exists"); requires `tokens[note_kind]` to be set; pulls `value` tokens from `msg.sender` with `safeTransferFrom` (so it needs an ERC20 approval) into the consumer; records `{note_kind, amount, spent=false}`; emits `MintAdded`. It stores no registrant, checks neither hash nor value non-zero, and no function cancels or refunds a registration (`mints[` appears only in `mint`, `mintWithAuthorization`, `verifyMint` and a getter). A second path, `mintWithAuthorization` (l.650), uses an EIP-3009 token authorization plus an EIP-712 signature by the funder over `(hash, value, kind, from, validity, nonce)`.
- *Settlement* (`verifyRollup` l.314–372): prover gate, verifier lookup and length check, root equals `old_root`, validator signatures over `(new_root, height, otherHash)`, **then** message dispatch, **then** the verifier call, then `rootHash = newRoot`, `blockHeight = height`, `RollupVerified`. `verifyMint` (l.418–440) requires `mints[hash].amount == value`, `mints[hash].note_kind == note_kind`, `!spent`; sets `spent = true`; emits `Minted`. No tokens move.
- *Ownership and recipient.* The circuit's ownership check (`noir/common/src/note.nr` `check_input_note_ownership`) applies to **input** notes with non-zero value; a mint's inputs are zero-value padding, so no ownership constraint applies to a mint. The output note's address is private and unconstrained relative to anyone. The public message carries no recipient, the registry stores no registrant, and the circuit never links `msg.sender` of the registration to the note owner. **No recipient guarantee is established by this code, and I assert none.**

**Protocol-policy interpretation (not established by code)**
- The registration is the funding of the minted note: the escrow is the backing for credit created in the rollup and it stays in the consumer (burns later pay out of the contract's balance).
- The consumer's registration check protects mints against unbacked forgery: any forged mint record in an accepted block needs a funded, unspent, equal-value registration. Burns have no registration step in `verifyBurn`, so for burns the consumer relies on the proof alone. This asymmetry is an observation about the code, not a finding of a defect.
- "Anyone can call mint … on behalf of the user" (l.617) suggests the registrant need not be the note owner by design; whether validators check the registry off-chain before including a mint is outside this evidence.

**Unresolved**
- Why existence is tested as `amount != 0` (a zero-value registration can be repeated; an unregistered all-zero mint record passes `verifyMint`; whether a zero-value mint proof can exist was not examined).
- Whether the missing recipient/registrant binding is intended.
- Off-chain validator behavior; multi-validator and multi-message blocks.

## 3. The five cases (fresh deployments; real verifier; real consumer behind a proxy)

| # | Case | Outcome | Rejecting check / verifier reached | State change | Property |
|---|---|---|---|---|---|
| 1 | matching registration (100) + original mint proof | **accepted**, 4,299,087 gas | verifier called with exact `(proof, inputs)`; 2 events (`Minted`, `RollupVerified`) | root `0x0577…`→`0x1799…`, height 0→1, mint unspent→**spent**, consumer tokens 100 and minter 900 unchanged by settlement | holds |
| 2 | no registration + original proof | rejected, 21,435 gas | `Mint value invalid` (`verifyMint`); verifier **not** reached | none | holds |
| 3 | registration of the same identity with value 101 + original proof | rejected, 21,435 gas | `Mint value invalid`; verifier not reached | none (the 101 registration remains, unspent) | holds |
| 4 | original registration (100) + public value changed to 101, proof reused | rejected, 21,435 gas | `Mint value invalid`; verifier not reached | none | holds |
| 5 | zero-message T10 proof, no registration (root aligned by owner `setRoot`, as in T12) | **accepted**, 4,274,098 gas | verifier called; 1 event (`RollupVerified`) | root `0x12e4…`→`0x06cd…`, height 0→1, no mint entry or balance changed | holds (no obligation ⇒ nothing to consume) |
| 4b | *reference, not one of the five:* value 101 + a matching 101 registration | rejected, 2,079,441 gas | the **verifier**, `SumcheckFailed()`; reached with exact calldata | none (spent flag rolled back) | holds |

Execution order was observed, not assumed: for cases 2–4 the signature check (valid; it covers `new_root`, `height`, `otherHash`, which the alterations do not touch) and the message/registration check ran before the verifier, and case 4b shows the verifier is the backstop once the registration check passes. All rejected calls left root, height, the mint entry and every balance unchanged. In all six executions the property holds: **production behaviour satisfies it; no violating transition was found.**

## 4. What this says about the research

- **Reusable concepts.** *Identity* (an identifier carried in the proof-authenticated message that keys application state), *value* (amount equality between message and registration), *kind/asset* (which asset the amount is in), *backing* (a funded entry that exists before settlement and stays held), *single use* (a flag set in the same transaction), *atomic rejection* (unchanged state on any revert), and *vacuity* (no obligation, no state change). These map onto the T01–T07 vocabulary (deposit identity, exact amount, funded-and-unconsumed to consumed, unchanged on reject).
- **Payy-specific.** The variable-length message grammar (kind words; mint = four words), the identifier being a hash of private `psi` values rather than a row index, the note-kind encoding and token mapping, the check order (messages before verifier), the use of a `spent` flag with entries never deleted, escrow that stays in the consumer, `amount != 0` as existence, and the registry-key and validator machinery. There are no activation flags or prefix limits as in the batch fixture.
- **Not established.** Nothing about the advisory: its flaw is a circuit-side unconstrained message tail that could forge a *burn*; this experiment covers a legitimate *mint* and a consumer check that, for mints, would also constrain a forged record. No violating transition exists here, and no vulnerability status is claimed. Only one mint, one message type, one validator and a local token were tested.
- **BindCheck vs a direct assertion.** With the current manual specification they are **functionally equivalent**: the whole property, with its snapshot struct, decoder and helpers, is about 90 lines of direct Solidity (87 non-comment lines), and a checker would need exactly the same facts (grammar, identity, value, kind, single use). The specification, the Solidity property and the cases share one author and one reading of the sources, so agreement shows consistency, not that the reading is right. A meaningful comparison needs something this setup lacks: an independently written variant of the consumer with a missing check (clearly labeled if synthetic), or a cost measurement of how much of the specification and extraction transfers from the batch fixture to this case.

## 5. Limitations and smallest next task

Limitations: one mint of 100 raw units, one validator, a local ERC20 instead of USDC, no burn or multi-message block, no off-chain validator behavior, and the registrant/owner relationship untested beyond the absence of a code link. Foundry's recorder lists events emitted inside reverted frames: the reference case 4b records one consumer event although the call reverted (a chain would discard it), so event counts are meaningful only for accepted calls.

**Smallest next research task (T15):** apply this same property and the five cases to **labeled synthetic mutants of `verifyMint`** (for example, drop the amount check; drop the kind check; drop the `spent` update), each built as a separate copy and clearly marked synthetic, to learn whether the property plus this small case suite discriminates them. That would be the first test of the property on an implementation other than our own batch fixture, with no change to the circuit, verifier or production consumer.
