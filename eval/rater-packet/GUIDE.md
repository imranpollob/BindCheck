## 1. Background in two minutes

A zero-knowledge (ZK) application on Ethereum has three parts:

| Part | Language | Role |
|---|---|---|
| **Circuit** | Circom (`.circom`) | Defines the statement a proof establishes. Some signals are **public** (visible to the contract); the rest stay private. |
| **Verifier contract** | Solidity, usually generated by snarkjs (`Groth16Verifier`, `Verifier.sol`) | `verifyProof(proof, publicSignals)` returns true only if the proof is valid **for exactly those public signals**. It holds a hard-coded verification key. |
| **Consumer contract** | Solidity, hand-written | Calls the verifier, then **does something**: pays a recipient, mints tokens, marks a nullifier spent, records a vote. |

A proof only vouches for its **public signals**. Every other value the consumer
uses (function arguments, `msg.sender`, `msg.value`) is chosen freely by whoever
sends the transaction. Proofs are visible in the public mempool before they are
mined, so anyone can copy a pending proof and resubmit it with different
arguments (front-running).

## 2. What "binding" means

A value the consumer acts on is **bound** if the proof fixes it. That happens in one of three ways:

1. It is passed **as** a public signal to `verifyProof`, or computed only from public signals.
2. It is checked **equal** to a public signal before the effect happens (`require(pubSignals[2] == uint256(uint160(recipient)))`).
3. It is included in a public **commitment/hash** that the circuit opens.

```solidity
// UNBOUND: recipient and amount are chosen by the caller, not by the proof
function withdraw(uint[2] calldata a, uint[2][2] calldata b, uint[2] calldata c,
                  uint256 root, uint256 nullifier, address recipient, uint256 amount) external {
    require(verifier.verifyProof(a, b, c, [root, nullifier]));
    require(!spent[nullifier]);
    spent[nullifier] = true;
    payable(recipient).transfer(amount);              // anyone can copy the proof and redirect the funds
}

// BOUND: recipient and amount are public signals of the proof
    require(verifier.verifyProof(a, b, c,
        [root, nullifier, uint256(uint160(recipient)), amount]));
```

The study asks one narrow question per card: **is the binding problem the card
describes actually present in the code?** You do not need to build an exploit.

## 3. The six warning kinds

Each card names its kind (K1–K6) near the top.

### K1 Effect not bound: recipient, amount, identity, caller, call value, stored value
**Claim:** a value that decides *who* benefits, *how much*, or *what gets
recorded* is not fixed by the proof.

How to check:
1. Find the `verifyProof(...)` call (or the wrapper that calls it) in the flagged function.
2. List exactly what goes into the public-signal array.
3. Find the effect: `transfer`, `call{value:}`, `_mint`, `safeTransferFrom`, a storage write like `balances[x] += y` or `owner[id] = x`.
4. For each value in the effect (recipient, amount, token id, identity, `msg.value`), ask whether it is in the public signals, checked equal to one before the effect, or inside a proven commitment.

**TP** if some value in the effect is not bound. `msg.sender` counts as unbound
unless the proof contains the sender address. A copied proof sent by someone
else then benefits that someone else.

**FP** if every effect value is bound, or the unbound value cannot harm anyone
(for example an event field or a log message).

### K2 Replay key (nullifier) not bound to the proof
**Claim:** the value used to stop a proof being used twice (the nullifier,
"used" mapping key, or similar) is supplied by the caller rather than by the proof.

How to check:
1. Find the "spent" mapping: `require(!nullifiers[k]); ... nullifiers[k] = true;`.
2. Is `k` a public signal, or derived only from public signals?

**TP** if `k` is a separate argument not tied to the public signals. The same
proof can then be replayed with a fresh `k`. **Also TP** if the key is
checked but never marked spent, or marked spent but never checked.

**FP** if `k` comes from the public signals and is both checked and marked.

### K3 Replay key aliasing through the field (field representatives)
**Background:** circuits compute in the field of size
`r = 21888242871839275222246405745257275088548364400416034343698204186575808495617`.
Solidity integers go up to 2^256. If a verifier accepts a public signal `x`
without checking `x < r`, then `x` and `x + r` (and `x + 2r`, ...) describe the
same field value, and the same proof verifies for all of them. A contract that
uses the raw integer as a mapping key then sees "new" nullifiers and accepts
the replay.

**Claim:** the replay key is a public signal, but no `x < r` check on that
position exists in the verifier, and the contract keys its mapping by the raw
integer.

How to check:
1. Find which public-signal position is the replay key.
2. In the verifier, look for a rejecting check on that position against `r`
   (see §6: `checkField` with `lt(v, r)`, or `require(input[i] < SNARK_SCALAR_FIELD)`).
3. Check whether the consumer reduces or guards the key itself (`k % r`, `require(k < r)`).

**TP** if neither the verifier nor the consumer rejects values `>= r` at that
position. If the check compares against **`q`** instead of `r` (§6), it is still TP:
add tag `[Q-GUARD]`. Such an alias exists only for small keys, so the practical
impact is low.

**FP** if a correct `< r` check exists for that position, or the key is reduced
or guarded.

### K4 Verifier lacks a public-input range check
**Claim:** the verifier does not reject public signals `>= r` for **every**
position.

How to check: open the verifier (§6). Modern snarkjs verifiers call
`checkField(...)` once per position inside `verifyProof`. Count the calls and
compare with the number of public signals, then check the constant used.

**TP** if any position is unchecked, or the check uses `q` (tag `[Q-GUARD]`).

**FP** if every position is checked against `r`. The check may live in a
wrapper that copies the inputs to the generated verifier; that counts.

### K5 Verifier key is forgeable (γ = δ) or has duplicate IC points
**Background:** a Groth16 verification key contains points `alpha`, `beta`,
`gamma`, `delta` and `IC0..ICn`. If **gamma equals delta**, anyone can forge a
proof for any public signals. Choose A = alpha, B = beta, C = −vk_x; the
pairing equation `e(A,B) = e(alpha,beta)·e(vk_x,gamma)·e(C,delta)` then holds.
This happens when a project exports its verifier from an **uncontributed**
snarkjs key (`*_0000.zkey`). That key is for testing only: both gamma and delta
are the generator point.

How to check: in the verifier, compare the four gamma constants with the four delta constants:
```solidity
uint256 constant gammax1 = ...;  uint256 constant deltax1 = ...;
uint256 constant gammax2 = ...;  uint256 constant deltax2 = ...;
uint256 constant gammay1 = ...;  uint256 constant deltay1 = ...;
uint256 constant gammay2 = ...;  uint256 constant deltay2 = ...;
```
Older verifiers write `vk.gamma2 = Pairing.G2Point([...],[...]); vk.delta2 = Pairing.G2Point([...],[...]);`.
The default generator starts with `11559732032986387107991004021392285783925812861821192530917403151452391805634`.
Duplicate IC: two `IC` points with identical coordinates.

**TP** if all four coordinates are equal, in a verifier the application uses (§7).

**FP** if any coordinate differs, or the file is clearly not used by the application.

### K6 Public-signal count or order mismatch
**Claim:** the consumer passes a different number of public signals, or the
same number in a different order, than the verifier or circuit expects.

How to check:
1. **Consumer:** count the elements it passes to `verifyProof`.
2. **Verifier:** `uint[N] calldata _pubSignals` gives N. The number of `IC`
   points is N + 1 (`IC0` … `ICN`).
3. **Circuit:** find `component main {public [a, b]} = T(...);`. The public signals are:
   - every `signal output` of `T`, in declaration order;
   - then the inputs listed in `public [...]`, in the order they are declared in `T`.
4. Compare the counts, and where you can, the meaning of each position.

**TP** if the counts differ, or a value sits in a position that means
something else in the circuit (for example the consumer treats position 0 as
the nullifier but the circuit's first public signal is an output flag).

**FP** if the counts and order agree. A common cause is that the analysis
forgot that outputs are public signals.

## 4. Labels and tags

| Label | Use when |
|---|---|
| **TP** | The problem the card describes **is present** in the code at (or reached from) the flagged location. No exploit needed. |
| **FP** | The problem **is not present**: the value is bound, the guard exists, the counts match, the keys differ. Also FP if the flagged code is **not part of the application** (tests, mocks, deploy scripts, examples, dead copies), or the behaviour is **documented as intended** and harms no one. |
| **unclear** | You cannot decide within about 10 minutes, for example because files are missing or you'd need deployment or protocol knowledge you don't have. |

**Reason (one line, required).** Cite file:line, for example:
- `TP: recipient arg not in pubSignals (Pool.sol:61), paid at :92`
- `FP: amount = pubSignals[3], require at Pool.sol:75`
- `FP [TEST-CODE]: file under test/mocks`
- `unclear: verifier implementation not in repo`

**Tags (optional, in square brackets in the reason).** They let the study separate special cases:

| Tag | Meaning |
|---|---|
| `[ALWAYS-TRUE]` | The verifier the consumer uses is a mock that accepts every proof |
| `[ALWAYS-FALSE]` | The verifier is a placeholder that rejects every proof |
| `[Q-GUARD]` | The range check uses the base field `q` instead of `r` |
| `[TEST-CODE]` | Flagged code is a test, mock, script or example |
| `[UNUSED]` | Flagged file is not deployed or imported by the application |
| `[INTENDED]` | Code or docs say the behaviour is deliberate |
| `[DEMO]` | The project itself says it is a demo or hackathon prototype (still label normally) |

Placeholder verifiers: label the card's concern on its own terms, and add the
tag. For example, a recipient that isn't bound is TP even if the current
verifier is a stub; write `TP [ALWAYS-FALSE]: ...`.

## 5. Per-card procedure (2–5 minutes typical, 10 minutes maximum)

1. Read the kind (K1–K6) and the concern at the top of the card.
2. Read the code excerpt. If you need more context, open the **local copy**
   (path given on the card, under `sources/`) or the **GitHub link**. Both are
   pinned to the analysed commit.
3. Find the `verifyProof` call and write down the public-signal list.
4. Apply the checklist for that kind (§3).
5. Fill the row with the same `warning_id` in your sheet: `label` and `rater_reason`.

Label each card on its own, even when several cards look similar.

## 6. Reference

**Field constants (BN254)**
- Scalar field, correct for public signals:
  `r = 21888242871839275222246405745257275088548364400416034343698204186575808495617`
- Base field, wrong for public signals:
  `q = 21888242871839275222246405745257275088696311157297823662689037894645226208583`

Both start with `2188824287183927522224640574525727508`, so compare the **last digits**: `...5617` is r and `...8583` is q.

**Modern snarkjs verifier (shape)**
```solidity
contract Groth16Verifier {
    uint256 constant r = 21888...5617;   // scalar field
    uint256 constant q = 21888...8583;   // base field (used for proof points)
    uint256 constant gammax1 = ...; /* gammax2, gammay1, gammay2 */
    uint256 constant deltax1 = ...; /* deltax2, deltay1, deltay2 */
    uint256 constant IC0x = ...; uint256 constant IC0y = ...;   // IC0..ICN
    function verifyProof(uint[2] calldata _pA, uint[2][2] calldata _pB,
                         uint[2] calldata _pC, uint[N] calldata _pubSignals) public view returns (bool) {
        assembly {
            function checkField(v) {
                if iszero(lt(v, r)) { mstore(0, 0) return(0, 0x20) }   // rejects v >= r
            }
            ...
            checkField(calldataload(add(_pubSignals, 0)))    // position 0
            checkField(calldataload(add(_pubSignals, 32)))   // position 1
```
If `checkField` uses `lt(v, q)`, that is the wrong field (`[Q-GUARD]`).

**Older verifier (Pairing library style)**
```solidity
vk.gamma2 = Pairing.G2Point([..],[..]);  vk.delta2 = Pairing.G2Point([..],[..]);
vk.IC = new Pairing.G1Point[](N + 1);
for (uint i = 0; i < input.length; i++) {
    require(input[i] < snark_scalar_field, "verifier-gte-snark-scalar-field");
```

**Signs of a placeholder verifier:** `return true;` or `return false;` with no
pairing code, comments like "mock", "TODO", "replace with real verifier", or
contract names like `MockVerifier`.

## 7. Hard cases

- **Is it part of the application?** Contracts under `contracts/` or `src/`
  that are deployed, or imported by deployed code, count. When a project has
  two copies of a verifier and you can't tell which one is deployed, treat
  both as part of the application. Files under `test/`, `mocks/`, `script/`
  or `examples/` don't count, unless the main contracts import them.
- **The verifier body is missing on the card.** The tool sometimes matched an
  interface. Look in `sources/` or on GitHub for the implementing contract
  (`Groth16Verifier`, `Verifier`, `PlonkVerifier`). K1, K2 and K6 can usually
  be decided from the consumer and circuit alone. K3–K5 need the verifier; if
  you can't find it, label unclear.
- **Not a Groth16 verifier** (PLONK, Honk, STARK). K3 and K6 still apply in
  spirit. For K5 the key layout differs, so label unclear unless it's obvious.
- **The GitHub repository was deleted or renamed.** Use the local copies.
  If a file you need isn't included, label unclear.
- **Both the tool and the project look wrong in a different way.** Label only
  the concern on the card, and mention the other issue in your reason if you like.

## 8. Glossary

- **Public signals / public inputs:** values the proof is about, passed to
  `verifyProof` as an array.
- **Nullifier:** a per-proof value recorded on-chain so the same secret cannot be used twice.
- **Field element:** an integer modulo r; the circuit cannot tell `x` from `x + r`.
- **Groth16:** the proof system used by snarkjs/Circom by default.
- **IC points:** one key point per public signal (plus IC0); N + 1 points means N public signals.
- **Front-running:** copying a pending transaction's data and submitting your own version first.
- **Commitment:** a hash of values that the circuit proves knowledge of; binding through a commitment counts as bound.
